# Learning notes

One section per piece: what it does, why this way, one rejected alternative, and likely

## M1 piece 1: Issue entity + SourceType enum + IssueRepository (3 Nov 2026)

Files:
- `src/main/java/com/saisanketh/triage/domain/SourceType.java`
- `src/main/java/com/saisanketh/triage/domain/Issue.java`
- `src/main/java/com/saisanketh/triage/repository/IssueRepository.java`

### What it does
- `SourceType` is an enum with one value, `GITHUB`. It says which tracker an issue came from.
- `Issue` is a JPA entity: one Java object = one row in the `issue` table from `docs/schema.md`.
  Each field has a `@Column` that sets the column name, length and whether it can be null.
  The labels are a `Set<String>` stored in a second table, `issue_label`.
- `IssueRepository` is an interface. Spring Data writes the code for it at startup, so we get
  `save`, `findById`, `findAll` and so on for free. We add one method,
  `findBySourceAndExternalId`, which piece 5 (upsert) uses to ask "have we stored this issue already?"

### Why this way
- **The table is created from the entity** (`ddl-auto: update`), so the annotations carry the
  whole schema: the unique constraint `(source, external_id)` and the index `(repo, created_at)`
  are declared in `@Table`, and the label index in `@CollectionTable`. Checked in Postgres
  with `\d issue`: it matches `docs/schema.md`.
- **`@Enumerated(EnumType.STRING)`** stores `'GITHUB'`, not `0`. With the default (ORDINAL),
  adding or reordering enum values would silently change what old rows mean.
- **`Instant` for times**: an `Instant` is one exact moment in UTC, and Hibernate maps it to
  `timestamptz`. GitHub sends UTC times, so nothing is lost or shifted.
- **`raw` as `String` + `@JdbcTypeCode(SqlTypes.JSON)`**: Postgres stores it as `jsonb` (it checks that
  it is valid JSON and can index into it later), but in Java it's a plain string. We never
  read fields from it in Java, so a string is enough.
- **`columnDefinition = "text"`** for title, body and URL: a plain `String` would become
  `varchar(255)`, and long issue bodies would fail to insert.
- **Labels as `@ElementCollection`**: a label here is just a name with no id of its own, so
  it doesn't need its own entity. `Set` (not `List`) means the same label can't appear twice,
  which matches the primary key `(issue_id, label_name)`. `@OnDelete(CASCADE)` puts
  `ON DELETE CASCADE` on the foreign key, as in the schema.
- **Lombok `@Getter @Setter @NoArgsConstructor`, not `@Data`**: `@Data` also generates
  `equals`, `hashCode` and `toString` from all fields. On an entity that is a trap: the id
  changes from null to a value on save (so `hashCode` changes and the object gets "lost" in
  a `HashSet`), and `toString` would touch the lazy `labels` collection and print the
  whole `raw` JSON. JPA needs the no-args constructor; setters are used by the mapper in piece 4.

### One alternative I rejected
**Writing the schema as SQL with Flyway** (`V1__create_issue.sql`) and setting
`ddl-auto: validate`. That is what I'd use in production: every schema change is a
versioned, reviewed file. I didn't do it now because it adds a dependency (the rules say ask first)
and `ddl-auto: update` is fine for a single developer while the schema is still changing.
Worth switching before M3, see the gotcha below.

### Two things Hibernate did differently from docs/schema.md
1. `id` is `bigint generated by default as identity`, not `bigserial`. These work the same way.
   Identity columns are the SQL-standard form and are preferred in modern Postgres.
2. Hibernate added `CHECK (source = 'GITHUB')` because the column is an enum. **Gotcha:** when
   we add `JIRA`, `ddl-auto: update` will *not* update this check, so inserts of Jira issues
   will fail until the constraint is changed by hand (or by a Flyway migration).

### Likely interview questions
1. **Why is the unique key `(source, external_id)` and not just `external_id`?**
   Ids are only unique within one tracker. A GitHub id and a Jira id could collide.
   Together they identify an issue anywhere, and they're what makes the backfill safe to re-run:
   find by that key, update if found, insert if not.
2. **Why `EnumType.STRING` instead of the default?**
   ORDINAL stores the position (0, 1, …). If someone adds a value in the middle of the enum,
   every existing row now points at the wrong value, and no error is raised. STRING stores the
   name, so it's readable in SQL and safe to extend.
3. **Why not use `@Data` on a JPA entity?**
   Its generated `equals`/`hashCode` use every field, including the generated id, which is
   null before save and set after, so the hash changes. Its `toString` can trigger lazy loading
   (or a `LazyInitializationException`) and dump huge fields. Use `@Getter`/`@Setter` and only
   write `equals`/`hashCode` if you need them (based on the id or the natural key).

## M1 piece 2: IssueSource + GitHubIssueSource, one page (3 Nov 2026)

Files:
- `src/main/java/com/saisanketh/triage/github/IssueSource.java`
- `src/main/java/com/saisanketh/triage/github/IssuePage.java`
- `src/main/java/com/saisanketh/triage/github/GitHubIssueSource.java`
- `src/test/java/com/saisanketh/triage/github/GitHubIssueSourceTest.java`
- `src/main/resources/application.yml` (new `github:` block)

### What it does
- `IssueSource` is an interface with one method: `fetchPage(owner, repo)`. The rest of the app
  will depend on this interface, not on GitHub directly.
- `IssuePage` is a Java `record` (a small immutable data class) holding two things: the list of
  issues as raw JSON (`JsonNode`), and the raw `Link` header (which tells us the URL of the next
  page; piece 3 reads it).
- `GitHubIssueSource` implements the interface. It sends
  `GET https://api.github.com/repos/{owner}/{repo}/issues?state=all&per_page=100` with three headers:
  `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28` (pins the API
  version so GitHub can't change the response under us) and `Authorization: Bearer <token>`.
- The token comes from the environment: `application.yml` has `token: ${GITHUB_TOKEN:}`, which
  means "use the env var GITHUB_TOKEN, or empty if it isn't set". The code never contains a token.

### Why this way
- **RestClient**: Spring's modern synchronous HTTP client (Spring 6.1+). It reads like a sentence
  (`get().uri(...).retrieve().toEntity(...)`) and throws an exception on 4xx/5xx by default.
- **`toEntity(...)`, not `body(...)`**: `body` gives only the JSON; `toEntity` also gives the
  response headers, and we need the `Link` header.
- **URI template `{owner}/{repo}`**: RestClient fills in and URL-encodes the values, so a strange
  repo name can't break the URL.
- **`JsonNode`, not a Java class per field**: we store the full JSON in the `raw` column anyway,
  and piece 4 picks out the fields it needs. Note: Spring Boot 4 uses **Jackson 3**, so the
  import is `tools.jackson.databind.JsonNode` (Jackson 2 was `com.fasterxml.jackson...`).
- **No token = warning, not a crash**: public repos work without a token, but only for 60
  requests/hour (5,000 with a token). Crashing at startup would also stop work that
  doesn't touch GitHub.
- **Two constructors**: Spring uses the public `@Autowired` one, which reads the config. The test
  uses the package-private one and passes in a `RestClient.Builder` bound to a fake server.
  Spring Boot 4 only auto-configures a `RestClient.Builder` bean if the `spring-boot-restclient`
  module is on the classpath, and it isn't (adding it would be a new dependency), so we
  call `RestClient.builder()` ourselves.
- **Test with `MockRestServiceServer`**: it replaces the HTTP layer inside RestClient, so the test
  checks the real URL, headers and JSON parsing, but never touches the network. 4 tests:
  correct request + items + Link header; last page has no Link header; no token = no
  `Authorization` header; 404 throws `HttpClientErrorException.NotFound`.

### One alternative I rejected
**Mocking `RestClient` itself with Mockito.** RestClient is a fluent chain
(`get()` -> `uri()` -> `retrieve()` -> ...), so you'd have to mock every step, and the test would
only prove we called methods in a certain order, not that the URL or headers are right.
`MockRestServiceServer` tests what actually goes over the wire.

### Likely interview questions
1. **Why put an interface (`IssueSource`) in front of GitHub?**
   So the code that uses it (backfill, upsert) doesn't depend on GitHub. A Jira source can
   implement the same interface, and tests can pass in a fake. The tradeoff is one extra file,
   which is worth it here because the schema is already designed to work with any tracker.
2. **How do you keep the GitHub token out of the code and out of git?**
   It is only in an environment variable. `application.yml` says `${GITHUB_TOKEN:}`, so Spring
   reads it at startup. The repo only contains the variable's *name*. In production it would come
   from a secret store and be injected as an env var.
3. **What does `MockRestServiceServer` do, and why is it better than calling the real API in a unit test?**
   It plugs in a fake HTTP layer that checks the outgoing request (URL, method, headers) and
   returns a canned response. The test is fast, works offline, never hits the rate limit, and can
   simulate cases that are hard to get from the real API, like a 404 or a page without a Link header.

## M1 refactor + pieces 3 and 4: neutral IssueSource, Link-header paging, PR skip, mapper (3 Nov 2026)

Files:
- moved to `source/`: `IssueSource.java`, `IssuePage.java` (new shape)
- `github/GitHubIssueSource.java` (paging + PR skip), new `github/GitHubIssueMapper.java`
- tests: `GitHubIssueSourceTest.java` (8 tests), new `GitHubIssueMapperTest.java` (4 tests),
  fixtures in `src/test/resources/github/`

### What it does
- **The interface now speaks only "our" language.**
  `IssuePage fetchPage(String repo, String cursor)` returns `IssuePage(List<Issue> issues, String nextCursor)`.
  Callers pass `null` for the first page, then keep passing back `nextCursor` until it is `null`.
- **Paging (piece 3).** GitHub puts the next page's URL in the `Link` response header:
  `<https://api.github.com/repositories/6296790/issues?...&after=Y3Vy...%3D&page=2>; rel="next"`.
  `nextUrl()` finds the part marked `rel="next"` and strips the `< >`. That URL *is* the cursor.
- **Pull requests skipped (piece 4).** GitHub's issues endpoint also returns PRs; only PRs have a
  `pull_request` field, so we drop those.
- **Mapping (piece 4).** `GitHubIssueMapper.toIssue(json)` copies each field into an `Issue`.
  Nested fields: `type.name` -> issueType, `milestone.title` -> milestone, `labels[].name` -> labels.
  The whole JSON goes into `raw` unchanged. `duplicate_of` stays null (a later step fills it).

### Why the interface hides GitHub details
Before the refactor, `IssuePage` returned GitHub JSON and GitHub's `Link` header, and took
`owner, repo` separately. So any caller (the upsert service, the backfill endpoint) would have
to know GitHub's JSON field names and how GitHub paging works. Now:
- **Callers depend only on `Issue` and an opaque cursor.** The upsert service in piece 5 never
  imports anything from `github/`. If GitHub changes its paging (it already moved from `page=N`
  to an encoded `after=` cursor), only `GitHubIssueSource` changes.
- **A Jira source fits without changing callers.** Jira pages with `startAt` numbers, not Link
  headers. A `JiraIssueSource` can use `"100"` as its cursor; the caller's loop stays the same.
- **Tests get easier.** Piece 5 can test the upsert with a tiny fake `IssueSource` that returns
  hand-made `Issue` objects, without any HTTP or JSON.
- The package name says the same thing: `source` is neutral, `github` is one implementation.
This is the **Dependency Inversion** idea: high-level code (backfill) depends on an
abstraction (`IssueSource`), and low-level details (GitHub HTTP) also depend on it.

### Why this way (other choices)
- **Mapper in its own class**: `GitHubIssueSource` does HTTP and paging; `GitHubIssueMapper` does
  JSON -> Issue. Each can be tested alone: the mapper test needs no fake server at all.
- **Repo name taken from GitHub's `repository_url`, not from what the user typed**: GitHub accepts
  `Spring-Projects/Spring-Boot` in URLs, but then the same repo would be stored under two
  spellings. GitHub's own value is always the same.
- **`String.valueOf(json.get("id").asLong())`**: real ids are already bigger than an `int`
  (#52529 has id 6154714728), so `asInt()` would give a wrong number.
- **`URI.create(cursor)`, not `.uri(cursor)`**: the cursor is already URL-encoded (`%3D` means `=`).
  A plain string is treated as a template and encoded *again* (`%3D` -> `%253D`), and GitHub would
  get a broken cursor. Checked: switching to `.uri(cursor)` makes the paging test fail with
  exactly that `%253D`.
- **Only follow cursors that start with `https://api.github.com/`**: every request carries our
  token. If a bad cursor pointed at another server, we'd send it the token. Note the trailing
  `/`: without it, `https://api.github.com.evil.example.com` would pass the check.
- **Loop until `nextCursor` is null, not until a page is empty**: after skipping PRs, a page can
  have zero issues and still have more pages behind it.

### One alternative I rejected
**Paging by page number** (`?page=1`, `?page=2`, ... until an empty page). It looks simpler, but
GitHub's real next links use an `after=` cursor, the Link header is the documented way to page,
and a "stop on empty page" loop would stop too early on a page that held only PRs.

### Basics: the annotations and libraries used here
- **`@Component`** (Spring): marks a class so Spring creates one instance of it at startup (a "bean")
  and can hand it to other classes.
  *Before:* `GitHubIssueMapper mapper = new GitHubIssueMapper();` written by hand everywhere.
  *After:* put `@Component` on the class, and Spring creates it once and passes it in.
- **Constructor injection + `@Autowired`**: Spring calls the constructor and fills each parameter
  with a matching bean. That's how `GitHubIssueSource` gets the mapper.
  *Example:* `public GitHubIssueSource(..., GitHubIssueMapper mapper)` -> Spring passes the mapper.
  `@Autowired` is only needed here because the class has two constructors, so Spring must be told
  which one to use. With a single constructor, Spring uses it automatically.
- **`@Value("${github.token}")`** (Spring): fills a parameter from configuration.
  *Before:* `String token = System.getenv("GITHUB_TOKEN");` *After:* `@Value("${github.token}") String token`,
  and `application.yml` says `token: ${GITHUB_TOKEN:}` (env var, or empty).
- **`@Slf4j`** (Lombok): generates a logger field for you.
  *Before:* `private static final Logger log = LoggerFactory.getLogger(GitHubIssueSource.class);`
  *After:* `@Slf4j` on the class, then just `log.warn(...)`.
- **`record`** (Java 16+): a short way to write a class that only holds data.
  *Before:* a class with 2 private final fields, a constructor, 2 getters, `equals`, `hashCode`, `toString`.
  *After:* `public record IssuePage(List<Issue> issues, String nextCursor) {}`; read with `page.issues()`.
- **`JsonNode`** (Jackson 3, package `tools.jackson.databind`): a tree view of any JSON.
  `json.get("milestone")` gives a child node, `.asString()` / `.asInt()` / `.asLong()` read values,
  `.has("pull_request")` checks for a field, `.isNull()` is true for JSON `null`.
  *Example:* `{"type": {"name": "Bug"}}` -> `json.get("type").get("name").asString()` is `"Bug"`.
  `json.toString()` writes the node back out as JSON text (used for `raw`).
- **`ParameterizedTypeReference<List<JsonNode>>`** (Spring): Java forgets generic types at runtime,
  so `List<JsonNode>.class` can't be written. This small anonymous subclass (`{}` at the end)
  keeps the full type so Spring knows to build a list of `JsonNode`.
- **`MockRestServiceServer`** (spring-test): sits inside RestClient instead of the real HTTP
  connection. `expect(requestTo(url))` says what request must arrive, `andRespond(withSuccess(...))`
  says what to answer. Expectations are checked in order, so the 2-page test also proves page 2
  was asked for *after* page 1, using exactly the cursor URL.

### Likely interview questions
1. **Why does `IssueSource` return a cursor string instead of a page number or GitHub's Link header?**
   Each tracker pages differently (GitHub: Link header URLs with an encoded `after` cursor; Jira:
   `startAt` numbers). An opaque cursor lets every source keep its own method, while callers
   always run the same loop: pass the cursor back until it is null.
2. **What could go wrong if you followed any cursor URL you were given?**
   Every request sends `Authorization: Bearer <token>`. A cursor pointing at another host would
   leak the token there (and it's a form of SSRF). So we only follow URLs that start with
   `https://api.github.com/`, including the slash, so `api.github.com.evil.com` is rejected.
3. **How do you know a GitHub item is a pull request, and why filter it in the source rather than later?**
   GitHub's issues endpoint returns PRs too, and only PRs carry a `pull_request` field. Filtering
   in the GitHub source keeps that GitHub quirk inside the GitHub code: callers only ever see real
   issues, and a Jira source never needs a PR concept.

## M1 finish, step A: IssuePage gets `skipped`, source types fully neutral (4 Nov 2026)

Files: `source/IssuePage.java`, `source/IssueSource.java`, `github/GitHubIssueSource.java`,
`GitHubIssueSourceTest.java` (9 tests now).

Most of step A (the move to `source/`, `fetchPage(repo, cursor)`, `List<Issue>` + `nextCursor`)
was already done in the previous commit. This step adds the last two things.

### What it does
- `IssuePage` now has a third field: `int skipped`, the number of items the tracker sent on
  this page that were *not* issues and were left out. For GitHub those are pull requests.
- `GitHubIssueSource` counts them: each item with a `pull_request` field adds 1 to `skipped`
  instead of being mapped.
- The two `source/` types no longer mention anything GitHub-specific, not even in comments.
  (`IssueSource` used to say "e.g. GitHub sent only pull requests"; now it says
  "every item on it was skipped".) The word "pull request" now only appears in `github/`.

### Why this way
- **Why count skipped at all?** The backfill summary (step D) reports pages, inserted, updated
  and skipped. Without the count, "we stored 30,000 issues" can't be checked against GitHub's
  total, because GitHub's list mixes issues and PRs.
- **Why the neutral name `skipped`, not `pullRequestsSkipped`?** A Jira source might skip other
  things (e.g. sub-tasks). The caller only needs "how many were left out"; *why* is the source's business.
- **Why count it now, in step A, not in step C?** The code already skipped PRs, so passing `0`
  would have been a wrong number. Counting is one `skipped++`.

### Basics: adding a field to a `record`
A record's constructor always takes *all* its fields in order. So
`record IssuePage(List<Issue> issues, String nextCursor)` -> `new IssuePage(issues, cursor)`
becomes
`record IssuePage(List<Issue> issues, String nextCursor, int skipped)` -> `new IssuePage(issues, cursor, skipped)`.
Every old `new IssuePage(a, b)` stops compiling. That's a good thing: the compiler shows you every
place that must now decide what `skipped` is, so none can be forgotten. A new accessor
`page.skipped()` comes for free.

### One alternative I rejected
**Let the caller work it out as `100 - page.issues().size()`.** This breaks on the last page
(which usually has fewer than 100 items), it bakes GitHub's page size into neutral code, and it
mixes up "skipped" with "there were fewer items". The source is the only place that knows
what it left out, so it reports it.

### Likely interview questions
1. **How do you keep an abstraction from leaking details of one implementation?**
   Look at its types and words: here `IssuePage` uses only our `Issue`, a `String` cursor
   nobody opens, and a count. No `JsonNode`, no Link header, no "pull request". If a Jira
   implementation would find a word meaningless, it doesn't belong in the interface.
2. **A page comes back with zero issues. Is the backfill finished?**
   Not necessarily: it could be a page of only PRs (`skipped = 100`) with more pages after it.
   The only "finished" signal is `nextCursor == null`. A test checks exactly this case.
3. **What happens when you add a field to a Java record that is already used?**
   The canonical constructor gets a new parameter, so every existing `new` call fails to compile
   until it passes a value. It's a breaking change, and the compiler helps by finding every call site.

## Setup change: Postgres on host port 5433, database renamed to `triage` (4 Nov 2026)

### What it does
`docker-compose.yml` now maps `"5433:5432"`: port 5433 on the Mac goes to port 5432 inside the
container. `application.yml` connects to `jdbc:postgresql://localhost:5433/triage`.

### Why
A Homebrew Postgres on the Mac already listens on `localhost:5432`, so the app was connecting
to *that* one (which has no `copilot` user) instead of the Docker one. The left number in a port
mapping is the host side, so changing only it avoids the clash; inside the container Postgres
still uses its normal port. The DB name `copilot` was left over from the old project name.

### Gotcha: `POSTGRES_DB` only works on an empty volume
The postgres image creates `POSTGRES_DB` only the *first* time it starts with an empty data
volume. Our volume already existed, so changing `copilot` -> `triage` in the file did nothing on
its own; I ran `CREATE DATABASE triage OWNER copilot` once. A fresh clone gets `triage`
automatically. (The old, empty `copilot` database is still in the volume and can be dropped.)

### One alternative I rejected
**Stopping the Homebrew Postgres** (`brew services stop postgresql`). It works, but it changes
sai's machine outside this project and breaks again the next time that service starts.

### Likely interview questions
1. **In `"5433:5432"`, which side is which?** Left = host (your machine), right = container.
   The app connects to the host side, `localhost:5433`.
2. **You changed `POSTGRES_DB` but the database didn't appear. Why?** The init step only runs
   when the data directory is empty; an existing volume keeps its old databases. Create it by
   hand or (if the data doesn't matter) recreate the volume with `docker-compose down -v`.
3. **How did you find the port clash?** The error was `role "copilot" does not exist`, which is
   odd for a DB we created with that user. `lsof -iTCP:5432 -sTCP:LISTEN` showed two
   listeners: a local `postgres` on 127.0.0.1 and Colima's forwarder on `*`. `localhost` hit the local one first.

## M1 finish, step B: oldest-first paging and rate limits (4 Nov 2026)

Files: `github/GitHubIssueSource.java`, `GitHubIssueSourceTest.java` (14 tests).
Link-header paging was already done (pieces 3+4); this step fills the gaps.

### What it does
- **Oldest first**: the first page URL now ends in `&sort=created&direction=asc`. GitHub keeps
  those settings inside the next-page cursor, so every page stays in date order. Checked on real
  data: spring-petclinic's first item is #1 from 2013.
- **Logs the rate limit every 10 pages**: GitHub sends `X-RateLimit-Remaining` (calls left this
  hour) and `X-RateLimit-Reset` (when the count refills, as Unix seconds) on every answer. Every
  10th page we log e.g. `Fetched 50 pages; rate limit remaining: 4950 (resets at 2026-11-04T11:00:00Z)`.
- **Waits and retries on a rate limit**: if GitHub answers 403 or 429 *because of the rate limit*,
  we wait and ask for the same page again, at most 3 times. How long we wait, in GitHub's order:
  1. `Retry-After: 5` -> 5 seconds.
  2. `X-RateLimit-Remaining: 0` -> until `X-RateLimit-Reset`, plus 1 second in case our clock differs.
  3. Neither (some "secondary" limits) -> 1 minute, as GitHub's docs advise.
  After 3 retries we stop with `"GitHub rate limit still exceeded after 3 retries for ..."`.
- **A 403 that is not a rate limit fails at once** (e.g. "Resource not accessible by personal
  access token"): retrying would never help, so we throw with a clear message that tells you to
  check the token. No error message contains the token (a test checks that).

### How we tell "slow down" from "not allowed"
GitHub uses 403 for both. It counts as a rate limit only if: the status is 429, or it's a 403 *and*
(`X-RateLimit-Remaining` is `0`, or a `Retry-After` header is present, or the message says
"rate limit"). Anything else is a real refusal.

### Basics used here
- **`Supplier<T>`** (Java): an object that holds "some code that gives back a T", run with `get()`.
  We need it because a retry must run *the same HTTP call again*.
  *Before:* the call is written once and runs once: `restClient.get()...toEntity(...)`.
  *After:* `getWithRateLimitRetry("first page", () -> restClient.get()...toEntity(...))`; the helper calls
  `request.get()` as many times as it needs.
- **`java.time.Clock`**: "what time is it?" as an object. Code that calls `Instant.now()` can't be tested
  at a fixed time; code that calls `clock.instant()` can. The app uses `Clock.systemUTC()`, the test uses
  `Clock.fixed(2026-11-04T10:00:00Z)`, so "reset in 30 s" really means 30 s.
- **The `Sleeper` interface**: same idea for waiting. The app passes `duration -> Thread.sleep(duration)`;
  the test passes `waits::add`, which just records the wait. So a test of "wait 31 seconds"
  finishes in milliseconds and can check the exact number.
- **`AtomicInteger`**: a counter that stays correct when two threads add to it at once (`count++` on a
  plain `int` can lose updates). The source is one shared Spring bean, and two backfills could run together.
- **`Thread.currentThread().interrupt()` after `InterruptedException`**: when someone asks a sleeping thread
  to stop, Java throws `InterruptedException` and *clears* the "please stop" flag. Setting it again
  passes the request on to whoever runs the thread, instead of silently swallowing it.
- **`MockRestServiceServer` with `times(4)`**: the same expectation answers 4 requests, which lets the
  test simulate "rate limited on every try".

### One alternative I rejected
**Spring Retry (`@Retryable`)** or **Resilience4j**. Both are good, but they're new dependencies
(not allowed without asking), and the wait time here comes from *GitHub's headers*, which
fixed-backoff annotations don't read easily. A 30-line loop is easy to read and test.
(Another rejected idea: wait proactively when `X-RateLimit-Remaining` gets low. It's nicer to GitHub,
but it wasn't asked for, and the retry already covers running out.)

### Likely interview questions
1. **How do you handle GitHub's rate limit?**
   On 403/429 with rate-limit signs, wait as long as GitHub says (`Retry-After`, else until
   `X-RateLimit-Reset`, else 1 minute), then retry the same page, at most 3 times; then fail clearly.
   Every 10 pages we log how many calls are left. With a token the limit is 5,000 requests/hour.
2. **Why not retry every 403?**
   A 403 can also mean "your token can't read this repo". Retrying that wastes time and hides the
   real problem. We only retry when the headers or message say it's a rate limit.
3. **How do you test code that waits for 30 seconds without the test taking 30 seconds?**
   Inject time and waiting: a fixed `Clock` decides "now", and a fake `Sleeper` records how long
   the code *would* sleep. The test then checks the exact wait (31 s) instantly.

## M1 finish, step D: upsert and backfill loop (piece 5) (4 Nov 2026)

Files: `service/IssueService.java`, `service/BackfillService.java`, `service/BackfillSummary.java`,
`service/UpsertResult.java`, `Issue.updateFrom(...)`; tests `IssueServiceTest` (2), `BackfillServiceTest` (2).

### What it does
- `IssueService.upsert(issue)`: looks the issue up by `(source, externalId)`. Found -> copy the new data
  onto our existing row (`updateFrom`) and save -> `UPDATED`. Not found -> save it -> `INSERTED`.
- `BackfillService.backfill("owner/name")`: starts with cursor `null`, fetches a page, upserts each issue,
  adds up the counts, follows `nextCursor` until it is `null`. Returns
  `BackfillSummary(repo, pages, inserted, updated, skipped, durationMs)`, and logs progress every 10 pages.

### Two deliberate differences from the step D prompt
1. **`backfill` is in `BackfillService`, not `IssueService`.** See "self-invocation" below: inside one class,
   `this.upsert()` would skip the transaction without any error.
2. **`upsert` does not overwrite `duplicate_of` with null.** The prompt says "copy all fields", but GitHub's
   JSON never contains `duplicate_of` (step F fills it). Copying null would erase the answer key every
   time the backfill is re-run. So it's copied only when the incoming value is not null.

### Basics used here
- **`@Service`** (Spring): the same as `@Component` (Spring creates one instance and injects it),
  but the name says "this holds business logic". Purely a label for readers.
- **`@RequiredArgsConstructor`** (Lombok): writes a constructor for every `final` field.
  *Before:* `public IssueService(IssueRepository issueRepository) { this.issueRepository = issueRepository; }`
  *After:* `@RequiredArgsConstructor` on the class; Spring uses that constructor to inject the repository.
- **`@Transactional`** (Spring): "run this method in one database transaction". Spring starts a transaction
  before the method and commits after it (or rolls back if it throws a RuntimeException). It works by
  wrapping the bean in a **proxy**: other beans call the proxy, the proxy opens the transaction, then
  calls the real method.
  **Self-invocation trap:** if a method in the *same* class calls `this.upsert()`, it calls the real object
  directly, the proxy is skipped, and no transaction starts, silently. That's why the loop is in another bean.
- **Managed entity / dirty checking** (JPA): an entity loaded inside a transaction is "managed": Hibernate
  remembers its state, and at commit writes whatever changed (an `UPDATE`) without being asked. So
  `issueRepository.save(row)` in the update path isn't strictly needed; it's there so the reader sees the write.
- **Replacing labels in an `@ElementCollection`:** call `labels.clear(); labels.addAll(newLabels)` on the
  *same* Set. Hibernate replaced our `HashSet` with its own tracking set (`PersistentSet`) when it loaded
  the row; assigning a brand-new `Set` would throw that tracking away.
- **`Optional<Issue>`** (Java): "an Issue, or nothing", instead of returning `null`. `isPresent()` / `get()`.
- **Mockito** (testing): `@Mock IssueRepository` is a fake that does nothing until told;
  `when(repo.find(...)).thenReturn(...)` gives it an answer; `verify(repo).save(x)` checks it was called.
  `@InjectMocks` builds the real `IssueService` with the mocks. In `BackfillServiceTest`, `thenAnswer`
  makes the mock remember saves in a `HashMap`, so the second run can "find" the first run's rows.
- **`System.nanoTime()` for durations:** `currentTimeMillis()` is wall-clock time and can jump (NTP sync,
  clock changes); `nanoTime()` only ever moves forward, so it's the right tool for "how long did it take".

### One alternative I rejected
**One transaction for the whole backfill** (put `@Transactional` on `backfill`). That would keep tens
of thousands of entities in memory until the end, hold one very long transaction, and one bad issue on
page 400 would roll back all 400 pages. One transaction per issue is slower, but simple and safe to resume.
(A middle ground, one transaction per page, is a possible later optimisation.)

### Likely interview questions
1. **How does your backfill stay safe to run twice?**
   Every issue is matched on `(source, external_id)`, the same columns as the database's unique constraint.
   Found -> update, not found -> insert. The test runs the same data twice: the second run inserts 0.
   If two runs raced, the unique constraint would reject the second insert instead of allowing a duplicate.
2. **Why didn't you put `backfill` and `upsert` in the same class?**
   `@Transactional` works through a Spring proxy. A call from inside the same class (`this.upsert()`)
   bypasses the proxy, so no transaction starts and nothing warns you. Splitting into two beans means
   `BackfillService` calls `IssueService` through the proxy.
3. **What is dirty checking?**
   Hibernate keeps a snapshot of every entity it loaded in the current transaction. At commit it compares
   each entity with its snapshot and writes an `UPDATE` for whatever changed. So changing a field on a
   managed entity is enough to save it.

## M1 finish, step E: `POST /backfill/{owner}/{repo}` (piece 6) (4 Nov 2026)

Files: `web/BackfillController.java`, test `web/BackfillControllerTest.java` (3 tests).

### What it does
`curl -X POST localhost:8080/backfill/spring-projects/spring-petclinic` runs the backfill and, when it's
done, answers with the summary as JSON:
`{"repo":"spring-projects/spring-petclinic","pages":12,"inserted":...,"updated":0,"skipped":...,"durationMs":...}`.
Errors come back as standard "problem details" JSON: unknown repo -> 404, bad repo name -> 400.

### Synchronous vs background: the trade-off
*Synchronous* (what we do): the HTTP request stays open until the backfill finishes.
- Good: dead simple; the caller gets the real result or the real error; easy to test; nothing to poll.
- Bad: spring-boot takes minutes, so the request is long. If the client (curl, a proxy, a load balancer)
  gives up, the caller loses the summary (the backfill itself keeps running on the server). It also ties
  up one web thread for the whole time, and nothing stops two people starting the same backfill at once.
*Background* (later): `POST` answers `202 Accepted` with a job id at once; the work runs on another
thread (`@Async`, or better a Kafka message, which this project already plans to use); `GET /jobs/{id}`
shows progress. More robust, but needs job state, a status endpoint and more tests. Fine to wait until
the backfill is triggered by something other than a developer with curl.

### Basics used here
- **`@RestController`** (Spring MVC): marks a class whose methods answer HTTP requests, and whose return
  values are written as JSON (it's `@Controller` + `@ResponseBody`).
  *Before (plain servlet):* read the URL, parse it, call the service, turn the result into JSON, write it to the response.
  *After:* `@PostMapping("/backfill/{owner}/{repo}") public BackfillSummary backfill(...)`; Spring does the rest.
- **`@PostMapping("/backfill/{owner}/{repo}")`**: this method handles `POST` to that path; `{owner}` and
  `{repo}` are placeholders. **`@PathVariable String owner`** puts the placeholder's value into the parameter.
  POST (not GET) because it *changes* data; a browser or crawler following a GET link must never start a
  backfill. A test checks that GET gives 405 Method Not Allowed.
- **Records as JSON:** Jackson writes a record's components as fields: `BackfillSummary(repo, pages, ...)`
  -> `{"repo": ..., "pages": ...}`. No annotations needed.
- **`@ExceptionHandler`**: "if this controller throws X, answer like this instead of a 500".
  **`ProblemDetail`** is Spring's built-in RFC 9457 error body: `{"status":404,"title":"Not Found","detail":"..."}`.
- **`MockMvc` standalone setup** (spring-test): sends fake HTTP requests to the controller in memory, through
  real Spring MVC (URL matching, JSON, exception handlers), without starting a server, the app or a DB.
  We use this instead of `@WebMvcTest` because in Spring Boot 4 that lives in an extra module
  (`spring-boot-webmvc-test`) we would have to add.
- **`jsonPath("$.inserted")`**: picks a value out of the JSON response; `$` is the root object.

### One alternative I rejected
**`@Async` with a fire-and-forget `202 Accepted`.** It looks like a one-line improvement, but then the caller
can't see the result or errors, there's no progress or job id, and failures only show up in the logs.
Doing background work properly needs job tracking, which is a bigger piece than this step.

### Likely interview questions
1. **Why is the backfill a POST and not a GET?**
   GET must be safe (no side effects): browsers prefetch links, crawlers follow them, proxies may repeat
   them. A backfill writes thousands of rows and uses rate limit, so it's a POST.
2. **What are the downsides of running the backfill inside the HTTP request?**
   Long request (clients/proxies may time out and lose the summary), a web thread is busy for minutes, no
   progress, and no protection against two runs at once. The fix is a background job (Kafka or `@Async`)
   that returns a job id immediately, plus a status endpoint.
3. **How do you test a controller without starting the whole app?**
   `MockMvcBuilders.standaloneSetup(new BackfillController(mockService))`: real MVC routing, JSON and
   exception handling, a Mockito mock for the service, no server and no database.

## M1 finish, step F: the answer key, `duplicate_of` (4 Nov 2026)

Files: `source/DuplicateSource.java`, `source/DuplicateLink.java`, `github/GitHubDuplicateSource.java`,
`service/DuplicateService.java`, `service/DuplicateSummary.java`, two new `IssueRepository` methods,
`POST /backfill/{owner}/{repo}/duplicates` in `BackfillController`; tests `GitHubDuplicateSourceTest` (18),
`DuplicateServiceTest` (2), one more controller test.

### What I found in the real data first (curl, 4 Nov 2026)
- **#52529** (closed as duplicate): the REST timeline has only `closed` (with `state_reason: duplicate`) and
  label events. **No comment, no `marked_as_duplicate` event, and nothing in REST says which issue it
  duplicates.** GitHub's **GraphQL** API does: `ClosedEvent.duplicateOf` = **#52519**. That's set when a
  maintainer uses "Close as duplicate of #N".
- **Only 178 spring-boot issues have `state_reason=duplicate`, but 2,011 have the `status: duplicate` label.**
  Old issues were back-filled by GitHub as `state_reason: completed` (not null, as `docs/problem.md`
  assumed), and 2023-2024 ones are often `not_planned`. So the label is the main signal, and the step
  checks both.
- A sample of 20 labelled duplicates from 2013 to 2026 showed four kinds:
  1. Recent ones: `ClosedEvent.duplicateOf` (e.g. #47366 -> #46944, #48342 -> #48300). Reliable.
  2. A maintainer comment: "Duplicate of #16381", "Duplicates https://github.com/spring-projects/spring-boot/issues/49910".
     (Search finds ~717 labelled duplicates with "Duplicate of" in a comment.)
  3. A comment pointing to **another repo**: "This is a duplicate of https://github.com/spring-projects/spring-framework/issues/31892".
     Can't be stored: `duplicate_of` is a number in the same repo.
  4. Vague or no link: "Yes, see #52367", "we fixed it in #1800", or no comment at all (common before ~2016).
- **Surprise:** on #16344 the maintainer wrote "Duplicate of #16381", but the GraphQL `MarkedAsDuplicateEvent`
  lists #16344 as the *canonical* one, the opposite way. So the event's direction isn't trusted;
  it's only read as "these two are linked".

### The rules ("only fill it when sure")
1. If the **latest** close was "close as duplicate of #N" -> **FOUND** (evidence `CLOSE_REASON`).
   Latest, because an issue can be closed, reopened and closed again (#52124).
2. Otherwise collect candidates from "marked as duplicate" links (the *other* issue of the pair; ignored if
   someone later un-marked it) and from **maintainer** comments (`OWNER`/`MEMBER`/`COLLABORATOR`) matching
   `duplicate(s|d) (of) #N | gh-N | https://github.com/<owner>/<repo>/issues/N`.
   Exactly one candidate -> **FOUND**; more than one -> **AMBIGUOUS**; none -> **NOT_FOUND**.
3. A FOUND original in another repo becomes **OTHER_REPO** (not stored). Self-references are ignored.
   "duplicated by #N" (other direction) and "see #N" (vague) deliberately don't match.
The summary counts every outcome: `checked = found + notFound + otherRepo + ambiguous`, and `found` is split by evidence.

### Basics used here
- **GraphQL**: one endpoint (`POST /graphql`); the request says exactly which fields it wants, as nested
  text. `query($number: Int!) { repository(...) { issue(number: $number) { ... } } }`. The `$number` values
  go in a separate `"variables"` object, so the query text never changes (no string-building, no injection).
  `... on ClosedEvent { duplicateOf { ... } }` means "if this item is a ClosedEvent, also give me these fields".
  GraphQL usually answers **HTTP 200 even on errors**, with an `"errors"` list; the code checks it.
- **`Pattern` / `Matcher`** (Java regex): `Pattern.compile(...)` once (it's slow to build), then
  `matcher(text)` and `while (m.find())` walks through every match; `m.group(1)` is the first `( )` part.
  `(?i)` makes it case-insensitive, `\\b` means "word boundary" (so "nonduplicate" doesn't match).
- **`@Query` + `@Modifying`** (Spring Data JPA): write the JPQL yourself when a method name can't express it.
  JPQL talks about *entities and fields* (`Issue i`, `i.stateReason`), not tables and columns.
  `left join i.labels l` joins the `@ElementCollection`, and `l` is then one label string.
  `@Modifying` marks an `update`/`delete` query (not a select); it needs a transaction, so the method has `@Transactional`.
  *Before:* load the issue (and maybe its labels), set the field, save. *After:* one `UPDATE issue SET duplicate_of = ? WHERE id = ?`.
- **`@Param("repo")`**: ties a method parameter to `:repo` in the query.
- **Lambda as a fake interface:** `DuplicateSource` has one method, so the test writes
  `DuplicateSource source = (repo, number) -> answers.get(number);`, a complete fake with no mocking library.
- **Records with a "compact constructor"**: `record Target(String repo, int number) { Target { repo = repo.toLowerCase(...); } }`
  runs before the fields are set, so every `Target` is stored lower-case and `equals` ignores case.

### One alternative I rejected
**Using any `#N` in a maintainer's comment** ("see #123", "like #123"). It would fill many more rows, but a
wrong answer key is worse than a missing one: the replay test (M3) would mark our model wrong when it is
right. So vague references count as NOT_FOUND, and the report says how many there are.
(Also rejected: REST timeline only. It's simpler, but it cannot see "close as duplicate of", the best signal.)

### Likely interview questions
1. **How did you build the ground truth for duplicates, and how do you know it's right?**
   From GitHub's own records, strongest first: "close as duplicate of #N" (GraphQL `ClosedEvent.duplicateOf`),
   then "marked as duplicate" links and maintainer comments like "Duplicate of #N", which must agree on one issue.
   Vague mentions are ignored, other-repo originals are counted but not stored, and the summary reports
   found / not found / ambiguous / other repo, so the coverage is visible, not hidden.
2. **Why did you need GraphQL when everything else uses REST?**
   The REST timeline for #52529 shows "closed, reason duplicate" but not *which* issue. Only GraphQL exposes
   `duplicateOf` on the close event. It needs a token, and errors come back as HTTP 200 with an `errors` list.
3. **What biases does this answer key have?**
   It favours recent issues (structured close reason) and duplicates a maintainer bothered to link; old ones
   with no link are missing. Also, maintainers mostly spot duplicates that *look* alike (docs/problem.md),
   so the key leans towards easier cases. We report the not-found share honestly.

## M1 finish, step G: `GET /repos/{owner}/{repo}/issues` (piece 7) (4 Nov 2026)

Files: `web/IssueController.java`, `service/IssueSummary.java`, `service/IssueList.java`,
`IssueService.listIssues`, two new `IssueRepository` methods, `application.yml` (`open-in-view: false`);
tests `IssueServiceListTest` (3), `IssueControllerTest` (4).

### What it does
`curl 'localhost:8080/repos/spring-projects/spring-petclinic/issues?page=0&size=20'` returns
`{"issues":[{"number":..,"title":..,"state":..,"stateReason":..,"labels":[..],"createdAt":..,"duplicateOf":..}],"page":0,"size":20,"total":N}`,
newest first. `size` must be 1-100, `page` 0 or more (else 400).

### The N+1 problem, and how this avoids it
Labels live in another table and are **lazy**: Hibernate loads them only when you first touch `issue.getLabels()`.
Load 20 issues (1 query), then read each one's labels (20 more queries) = **N+1 = 21 queries** for one page.
With 100 issues it's 101. It's invisible in the code and only shows as slowness or a wall of SQL in the log.
The fix: load issues *and* labels in one query, with a join. Two ways:
- **Fetch join** in JPQL: `select i from Issue i left join fetch i.labels where ...`
- **`@EntityGraph(attributePaths = "labels")`** on a repository method: "when you run this query, also fetch
  labels". Same SQL, no hand-written JPQL. Used here.

**But a collection fetch + paging don't mix.** With a join, one issue with 3 labels becomes 3 rows, so the
database can't do `LIMIT 20` on *issues*. Hibernate then loads **all** matching rows and pages in memory
(warning `HHH90003004`): for spring-boot that's every issue, for every page. So it takes two queries:
1. `findIdsByRepo(repo, pageable)`: just the 20 ids for this page, `ORDER BY number DESC LIMIT 20 OFFSET ..`,
   plus a `count(*)` for the total. (Spring Data runs the `countQuery` automatically for a `Page`.)
2. `findByIdInOrderByNumberDesc(ids)` with `@EntityGraph("labels")`: those 20 issues and their labels, in one join.
Total: **3 SQL statements per page (ids, count, issues+labels), whatever the page size.**

### Why a DTO, never the entity
- The entity's `labels` is lazy. Turning it into JSON *after* the transaction ends throws
  `LazyInitializationException`, or (with open-in-view on) silently fires N+1 queries while writing the response.
- The entity has `raw` (the whole GitHub JSON, KBs per issue) and `body`: we'd send far too much.
- The API would change whenever the table changes. A record (`IssueSummary`) is a fixed contract.

### Basics used here
- **`Pageable` / `PageRequest.of(page, size, sort)`** (Spring Data): "page 2, 20 per page, newest first". Pass it
  to a repository method and Spring adds `ORDER BY ... LIMIT ... OFFSET ...`.
  **`Page<T>`** is the answer: `getContent()` (this page) + `getTotalElements()` (all pages, from the count query).
- **`@EntityGraph(attributePaths = "labels")`**: tells this one query to fetch the lazy `labels` too (a join).
  *Before:* `findByIdIn(ids)` then 20 lazy loads. *After:* one query with `left join issue_label`.
- **Derived query names**: `findByIdInOrderByNumberDesc(ids)`: Spring reads the method name and builds
  `where id in (...) order by number desc`. No SQL written.
- **`@Transactional(readOnly = true)`**: a read-only transaction; Hibernate skips dirty checking at the end.
- **`@GetMapping` + `@RequestParam(defaultValue = "20") int size`**: reads `?size=50` from the URL, or uses 20.
- **`spring.jpa.open-in-view: false`**: Spring Boot's default (`true`) keeps a DB session open until the HTTP response is
  written, so lazy loading "just works" in controllers and JSON writing. That hides N+1 queries and holds DB connections
  longer. Turning it off makes a missed fetch fail loudly in development instead of being slow in production.
- **`ArgumentCaptor`** (Mockito): catches the argument a mock was called with, so the test can check the
  `Pageable` (page 3, size 20, sorted by number desc).

### One alternative I rejected
**`@BatchSize(size = 100)` on `labels`.** One annotation, and Hibernate then loads labels for up to 100
issues in one `IN (...)` query when the first one is touched: 1 + 1 queries instead of N+1. It's a good tool,
but it changes *every* place that reads labels and is less obvious to a reader than an explicit
"load these issues with their labels" method. (Also rejected: a single `@EntityGraph` + `Page` query, because of
the in-memory paging trap above.)

### Likely interview questions
1. **What is the N+1 problem and how did you avoid it?**
   Loading N parents with 1 query and then each lazy child collection with its own query: N+1 round trips.
   I page the ids first, then load those issues with `@EntityGraph(labels)`, one join. 3 statements per page.
2. **Why not just add `join fetch` to the paged query?**
   A collection join multiplies rows, so the database can't `LIMIT` by issue. Hibernate fetches everything and
   pages in memory (HHH90003004), which is fine for 20 rows and terrible for 30,000. Page the ids, then fetch.
3. **Why return DTOs instead of entities?**
   Lazy collections break (or cause hidden queries) during JSON writing, entities carry fields the API shouldn't
   expose (`raw`, `body`), and the API contract shouldn't change every time the table does.

### What it does
- **Flyway owns the schema now.** On startup Flyway looks at its table `flyway_schema_history`, sees which
  `V<n>__*.sql` files have not run yet, and runs them in order, each exactly once.
- **V1** is the schema as it was (from `pg_dump --schema-only`), minus Hibernate's `CHECK (source = 'GITHUB')`.
  **V2** drops that CHECK with `IF EXISTS` (the old DB has it; a fresh one built from V1 doesn't).
- **The existing DB (44,204 rows) was "baselined":** `baseline-on-migrate: true` + `baseline-version: 1` means
  "this DB already has V1's tables; record it as version 1 without running V1". Then only V2 ran.
  Checked: history shows `1 << Flyway Baseline >>` and `2 drop source check`; the CHECK is gone; data intact.
- **`ddl-auto: validate`**: Hibernate no longer changes tables; at startup it only checks that every entity
  field has a matching column of a compatible type, and refuses to start otherwise.
- **Real-DB tests**: Testcontainers starts a throw-away `postgres:16` in Docker; Flyway builds it from V1 + V2
  (proving the migrations work on an empty DB); the tests run real SQL against it.

### Why not `ddl-auto: update` in production
- It only ever *adds* (new tables, new columns). It never drops or renames, never changes a type, and never
  migrates data. Rename a field and you get a second, empty column next to the old one.
- It's not reviewed or versioned: nobody sees the exact SQL before it runs on the production DB, and you
  can't tell which schema version a database is at.
- It adds things you didn't ask for, like our `CHECK (source = 'GITHUB')`, which would have rejected Jira rows,
  and it would never remove that CHECK by itself.
- Every app instance tries to change the schema when it starts; with several instances that's a race.
With Flyway every change is a SQL file in git: reviewed, versioned, run once, in order, on every environment.

### Basics used here
- **Flyway file names:** `V2__drop_source_check.sql` = version 2, description "drop source check" (two underscores).
  Never edit a file that has already run: Flyway stores a checksum and refuses to start if it changes. Add V3 instead.
  *Before:* change `Issue.java`, restart, hope Hibernate does the right thing. *After:* write `V3__add_x.sql`, review it, restart.
- **Baseline:** "adopt" a database that existed before Flyway. Without it, Flyway would try to run V1's
  `CREATE TABLE issue` on a DB that already has it, and fail.
- **Testcontainers:** a Java library that starts real Docker containers for tests and removes them afterwards.
  *Before:* tests against H2 (an in-memory DB that isn't Postgres: no `jsonb`, different SQL) or a shared dev DB.
  *After:* `new PostgreSQLContainer("postgres:16")`: the same database as production, fresh for each run.
- **`@ServiceConnection`** (Spring Boot): put it on a container bean and Boot points the DataSource (and Flyway)
  at that container. No URLs or passwords in test config.
- **`@DataJpaTest`**: starts only the database part of the app (entities, repositories, Flyway, JdbcTemplate).
  Each test runs in a transaction that is **rolled back** at the end, so tests can't see each other's rows.
  `@AutoConfigureTestDatabase(replace = NONE)` says "use our Postgres, don't swap in an embedded DB".
- **One container for all tests:** Spring caches a test context and reuses it for every test class with the
  same configuration. All real-DB classes extend `PostgresTest`, so the container starts once (~3 s), not per class.
- **Counting SQL statements:** with `hibernate.generate_statistics=true`, `Statistics.getPrepareStatementCount()`
  counts the statements Hibernate sent. The test asserts **exactly 3** for a page of 20 issues with labels.
- **`entityManager.flush()` then `clear()`:** flush sends pending SQL now; clear forgets every loaded entity,
  so the next read really goes to the database (like a new request).
- **Maven profile with file activation:** the `colima` profile turns itself on only if
  `~/.colima/default/docker.sock` exists, and tells Testcontainers where Docker is. On a normal Docker machine
  or in CI it stays off. (Running tests from VS Code doesn't use Maven, so there `DOCKER_HOST` must be set.)

### One alternative I rejected
**Recreating the database from V1 instead of baselining** (`docker-compose down -v`, then let Flyway run V1, V2
and re-run the backfill). Clean, but it throws away 44k rows and the answer key and costs ~30 minutes of API
calls. Baselining keeps the data and still gives a schema that V1 + V2 can rebuild from scratch (the tests prove that).
Also rejected: H2 for tests. It's fast but isn't Postgres (no `jsonb`, different SQL), so it would test the wrong database.

1. **How do you introduce Flyway into a project whose database already exists?**
   Write V1 = the current schema (from `pg_dump --schema-only`), set `baseline-on-migrate` with baseline version 1,
   so the existing DB is marked as V1 without running it. Further changes are V2, V3... Fresh databases (tests,
   new environments) run V1 for real. Make sure V1 + V2 give the same schema on both.
2. **Why `ddl-auto: validate` and not `update`?**
   `update` only adds, is not reviewed or versioned, races between instances, and even added a CHECK we didn't
   want. `validate` lets Flyway own the schema and still fails fast if an entity doesn't match the table.
3. **Why Testcontainers instead of H2 or mocks for repository tests?**
   Mocks don't run SQL at all; H2 runs a different SQL dialect. Testcontainers runs the real Postgres 16, so the

## M2 step 1: Kafka in docker-compose, topics `issue-events` and `issue-events.DLT` (4 Nov 2026)

Files: `docker-compose.yml` (service `kafka`), `kafka/KafkaTopicsConfig.java`, test `KafkaTopicsConfigTest` (2).

### What it does
- `docker-compose up -d` now also starts **one Kafka broker** (`apache/kafka:4.1.0`) on `localhost:9092`, in
  **KRaft mode**: the broker keeps its own metadata (which topics exist, who leads which partition), so no
  separate ZooKeeper service is needed.
- When the app starts, Spring's `KafkaAdmin` creates the two `NewTopic` beans if they don't exist:
  `issue-events` (3 partitions) and `issue-events.DLT` (3 partitions, for messages that keep failing).
  Checked with `kafka-topics.sh --describe`: both topics exist, 3 partitions, leader = broker 1.
- Auto-creating topics is switched off in the broker, so a typo in a topic name fails loudly.

### Partitions, keys and consumer groups: a small example
A **topic** is a named log of messages. It is split into **partitions**; each partition is an ordered list,
and Kafka only guarantees order *within* one partition.
The **key** decides the partition: `partition = hash(key) % 3`. We'll use the key `owner/repo#number`:
```
issue-events   partition 0: [octo/hello#7 opened] [octo/hello#7 labeled] [octo/hello#7 closed]   <- one issue, in order
               partition 1: [octo/hello#2 opened] [octo/web#5 edited]
               partition 2: [octo/hello#9 opened]
```
All events of issue #7 have the same key, so they land in the same partition and are read in the order they
were written: "closed" can't be processed before "opened".
A **consumer group** is a team of consumers sharing the work. Kafka gives each partition to exactly one member:
```
group "triage-worker", 1 instance  -> it reads partitions 0, 1, 2
group "triage-worker", 3 instances -> each reads one partition (3x the throughput)
group "triage-worker", 4 instances -> one sits idle: never more busy consumers than partitions
another group, e.g. "analytics"   -> gets its OWN copy of every message, independent of triage-worker
```
So partitions are the unit of parallelism (3 here), keys keep related messages in order, and groups let
different jobs each read everything.

### Basics used here
- **`NewTopic` + `TopicBuilder`** (Spring Kafka): describe a topic in code; `KafkaAdmin` creates it at startup.
  *Before:* run `kafka-topics.sh --create --topic issue-events --partitions 3 ...` by hand on every machine.
  *After:* `TopicBuilder.name("issue-events").partitions(3).replicas(1).build()` as a `@Bean`.
- **`@Configuration` + `@Bean`**: a class whose `@Bean` methods return objects for Spring to manage.
- **Replication factor**: how many brokers keep a copy of each partition. 1 here (one broker); production uses 3
  so a broker can die without losing messages.
- **Dead-letter topic (DLT)**: where a message goes after its retries are used up, so one bad message doesn't
  stop everything behind it in the partition. Same partition count as the main topic, because by default a
  failed message is sent to the *same partition number* in the DLT.
- **KRaft listeners**: `PLAINTEXT://:9092` is for clients, `CONTROLLER://:9093` for the broker's internal voting;
  `ADVERTISED_LISTENERS=localhost:9092` is the address the broker tells clients to use (the app runs on the Mac).

### One alternative I rejected
**The Bitnami or Confluent images, or ZooKeeper-based Kafka.** The prompt asks for the official Apache image,
it's what the Kafka project itself publishes, and ZooKeeper was removed in Kafka 4.0, so KRaft is the only
option going forward. Also rejected: a Docker volume for Kafka data. The image runs as a non-root user, so a fresh
volume needs ownership fixes, and in development Postgres, not Kafka, is the source of truth.

### Likely interview questions
1. **How do you keep events for one issue in order with 3 partitions?**
   Use the issue as the message key (`owner/repo#number`). The same key always hashes to the same partition, and
   Kafka keeps order within a partition. Different issues can still be processed in parallel.
2. **What happens if you run 5 consumers in a group on a 3-partition topic?**
   3 get one partition each; 2 are idle (standby). Partitions limit parallelism, so pick the count for the
   throughput you expect. Adding partitions later changes which partition a key maps to.
3. **What is KRaft?**
   Kafka's built-in consensus (Raft) for cluster metadata, replacing ZooKeeper. A node can be broker, controller
   or both; here one node is both. Since Kafka 4.0 it's the only mode.

## M2 step 2: webhook receiver `POST /webhooks/github` (4 Nov 2026)

Files: `github/WebhookSignatureVerifier.java`, `github/GitHubWebhookController.java`, `application.yml`
(`github.webhook-secret: ${GITHUB_WEBHOOK_SECRET:}`); tests `WebhookSignatureVerifierTest` (5),
`GitHubWebhookControllerTest` (9).

### What it does
GitHub sends an HTTP POST to us whenever something happens to an issue (a **webhook**). The receiver, in this order:
1. No secret configured -> **503** and an error log line `GITHUB_WEBHOOK_SECRET is not set: refusing ...`.
2. `X-Hub-Signature-256` missing or wrong -> **401**. The body is never logged.
3. `X-GitHub-Event: ping` (sent once when the webhook is created) -> **200** `pong`.
4. `issues` with action opened / edited / closed / reopened / labeled / unlabeled -> **200** (step 3 hands it to Kafka).
5. Any other event or action -> **202** "ignored". (A signed body that isn't JSON -> 400.)
It does no GitHub calls and no triage work: GitHub gives up after 10 seconds and marks the delivery as failed.

### How the signature works (HMAC)
GitHub and we share a secret. For each delivery GitHub computes `HMAC-SHA256(secret, body)` and sends it as
`sha256=<64 hex chars>`. We compute the same over the body we received; if both match, the sender knew the
secret (so it's GitHub) and the body wasn't changed on the way. Checked against GitHub's documented example:
secret `It's a Secret to Everybody`, body `Hello, World!` -> `sha256=757107ea...b043e17`.

### Why raw bytes, why constant time
- **Raw bytes:** the signature is over the *exact bytes* sent. If we parsed the JSON into an object and wrote it
  back out, spacing, key order or number formats could change and a genuine request would fail the check.
  So the controller takes `@RequestBody byte[]`, verifies, and only then parses.
- **Constant-time compare (`MessageDigest.isEqual`):** a normal `equals` stops at the first different character.
  An attacker can measure that tiny time difference and find the right signature one character at a time.
  `isEqual` always compares everything, so the time doesn't leak anything.

### Basics used here
- **`@RequestHeader(value = "X-GitHub-Event", required = false) String event`**: puts an HTTP header into a
  parameter (null if missing, instead of Spring answering 400 itself, so *we* decide: 401).
- **`@RequestBody byte[] body`**: the body untouched. *Before:* `@RequestBody IssueEvent event` (Spring parses
  JSON first; the original bytes are gone). *After:* `byte[]`, verify, then `jsonMapper.readTree(body)`.
- **`ResponseEntity`**: lets a controller choose the status code: `ResponseEntity.status(401).body("...")`,
  `ResponseEntity.accepted()` (202), `ResponseEntity.ok(...)` (200).
- **`javax.crypto.Mac`**: the JDK's HMAC. `Mac.getInstance("HmacSHA256")`, `init(new SecretKeySpec(secretBytes, ...))`,
  `doFinal(body)`; `HexFormat.of().formatHex(...)` turns the 32 bytes into 64 lowercase hex characters.
- **`JsonMapper`** (Jackson 3): Spring Boot creates one; we inject it and call `readTree(bytes)` to get a `JsonNode`.
- **Status codes:** 200 = done; 202 = received, nothing to do; 401 = we don't believe you're GitHub; 503 = we're not
  configured, try later (GitHub shows it as a failed delivery, which can be redelivered once the secret is set).

### One alternative I rejected
**A servlet filter or Spring Security for the signature check.** Cleaner if many endpoints needed it, but there's one
webhook endpoint, and a filter would have to cache the body so the controller can read it again (a body stream can
only be read once). Doing it in the controller with `byte[]` is short and visible. Also rejected: answering 401 when
the secret is missing. 401 means "you aren't GitHub", but the real problem is *our* configuration, so 503 plus a log line.

### Likely interview questions
1. **How do you know a webhook really came from GitHub?**
   HMAC-SHA256 of the raw body with a shared secret, compared with `X-Hub-Signature-256` in constant time. Wrong or
   missing -> 401, and the body is never logged. The secret comes only from an environment variable.
2. **Why must you verify the raw body before parsing JSON?**
   The signature covers the exact bytes. Parsing and re-serializing can change whitespace, key order or number
   format, so even a genuine request would fail, or you'd end up checking something other than what was sent.
3. **GitHub waits 10 seconds. How do you stay under that?**
   The receiver only verifies, reads the event type and hands the payload on (Kafka, step 3). No GitHub API calls,
   no triage. The slow work happens in a consumer that GitHub doesn't wait for.

## M2 step 3: idempotency on `X-GitHub-Delivery`, publish to Kafka (4 Nov 2026)

Files: `V3__webhook_delivery.sql`, `repository/WebhookDeliveryRepository.java`, `kafka/IssueEventMessage.java`,
`kafka/IssueEventPublisher.java`, `service/WebhookIntakeService.java`, `ClockConfig.java`, controller wired up,
producer timeouts in `application.yml`, `scripts/send-test-webhook.sh`, docs/schema.md. Tests:
`WebhookIntakeServiceTest` (3), `WebhookDeliveryDbTest` (2, real DB), 5 more controller tests.

### What it does
GitHub can send the same delivery more than once (its retries, or a person pressing "Redeliver"). Each delivery has
a unique `X-GitHub-Delivery` id. In **one transaction**:
1. `INSERT INTO webhook_delivery ... ON CONFLICT (delivery_id) DO NOTHING`. 0 rows inserted = we've seen it ->
   answer **200 "duplicate delivery"** and stop.
2. Publish to Kafka and **wait for the broker's ack** (`acks=all`, at most ~5 s).
3. Kafka failed -> exception -> the transaction **rolls back** (the delivery row disappears) -> **500**. Later,
   GitHub's Redeliver is treated as new and works.
The message: key `owner/repo#number` (same issue -> same partition -> in order), value
`{"deliveryId","action","repo","issue": {...GitHub's full issue object...}}`.

Checked by hand against the real app: first send 200 (0.26 s, mostly warm-up), same id again 200 "duplicate delivery"
(6 ms), wrong signature 401 (1 ms); Kafka had exactly 1 message, key `Codertocat/Hello-World#1`, partition 1.
With **Kafka stopped**: 500 in **2.05 s** and no delivery row; after starting Kafka, the same id was accepted.

### The trade-off, and the transactional outbox
The database and Kafka are two different systems, so one transaction can't cover both. Our order is
"insert row -> publish -> commit". What can go wrong:
- **Publish fails** -> rollback -> 500 -> nothing saved, nothing sent. GitHub can redeliver. Good.
- **Publish succeeds, then the commit fails** (DB dies in that millisecond) -> the message is in Kafka but the row
  isn't. A redelivery would publish it again: a **duplicate message**. Harmless here, because the consumer's upsert
  is idempotent (step 4), but in general it's a real gap.
- **We wait for Kafka inside a DB transaction**, so a slow Kafka holds a DB connection for up to ~5 s.
The proper fix is the **transactional outbox pattern**: in the *same DB transaction* write the delivery row **and**
an `outbox` row with the message; commit; answer 200. A separate relay (a poller, or Debezium reading the DB log)
then sends outbox rows to Kafka and marks them sent. Now the DB is the only thing that has to commit, nothing is
lost and nothing is sent unless it was saved. We're not building it yet: it needs another table, a relay process
and its own retries, and duplicate messages are already safe for us.

### Basics used here
- **Idempotency:** doing something twice has the same effect as doing it once. Here: the same delivery id twice ->
  one row, one Kafka message.
- **`INSERT ... ON CONFLICT DO NOTHING`** (Postgres): insert, or if the primary key already exists do nothing and
  report 0 rows, with no error and no race. *Before:* `SELECT` first, then `INSERT` (two requests at once can both
  see "not there" and both insert). *After:* one statement; the primary key decides.
- **`JdbcTemplate`** (Spring): run plain SQL. `jdbc.update(sql, args...)` returns the number of rows changed.
  It uses the same connection as JPA inside a `@Transactional` method, so it's in the same transaction.
- **`KafkaTemplate.send(topic, key, value)`** returns a `CompletableFuture`; `.get(5, SECONDS)` blocks until the broker
  answers or the timeout passes. *Before (fire-and-forget):* `send(...)` and hope. *After:* `send(...).get(...)`,
  so we only answer 200 when Kafka really has it.
- **`acks=all`**: the broker only confirms after the message is written to all in-sync replicas (here: 1).
- **Producer timeouts:** by default `send()` can block **60 s** waiting for metadata when Kafka is down. We set
  `max.block.ms=2000`, `request.timeout.ms=4000`, `delivery.timeout.ms=5000`, so the answer comes fast: 2 s when the
  broker is down.
- **Rollback rule:** Spring rolls a `@Transactional` method back when a *RuntimeException* escapes it, which is why
  `PublishFailedException` extends `RuntimeException`.
- **`@Transactional(propagation = NOT_SUPPORTED)` in a test:** `@DataJpaTest` normally wraps each test in a transaction
  that's rolled back. This turns that off for one test, so the service's own transaction really commits or rolls
  back and the test can check the table afterwards.
- **`@MockitoBean`** (Spring test): replaces one bean in the test context with a Mockito mock (here the Kafka
  publisher, so the real-DB tests don't need Kafka).

### One alternative I rejected
**Answer 200 first and publish in the background** (`@Async`). Fast, but if the publish then fails, GitHub already
thinks the delivery succeeded and will never resend it: the event is lost silently. Waiting for the ack keeps
"200" meaning "it's safely in Kafka". (The outbox, above, is the real upgrade; deferred for now.)

### Likely interview questions
1. **GitHub sends the same webhook twice. What happens?**
   The second `INSERT ... ON CONFLICT DO NOTHING` on the delivery id inserts 0 rows, so we answer 200 "duplicate
   delivery" and don't publish again. Even if a duplicate did get through, the consumer's upsert is idempotent.
2. **Kafka is down when a webhook arrives. What happens?**
   The publish times out after ~2 s, the exception rolls back the delivery row, and we answer 500. GitHub marks the
   delivery failed; when Kafka is back, "Redeliver" (or GitHub's retry) works because the id isn't stored.
3. **What is the transactional outbox pattern and why would you use it?**
   Write the business change and the outgoing message into the same database transaction (an outbox table); a
   separate relay publishes outbox rows to the broker. It removes the "DB committed but message not sent" (or the
   reverse) gap of writing to two systems, without distributed transactions.

## M2 step 4: the consumer (triage worker), out-of-order safety, retries and dead letters (4 Nov 2026)

Files: `kafka/IssueEventConsumer.java`, `kafka/KafkaErrorHandlingConfig.java`, `IssueService.upsert` (STALE rule),
`UpsertResult.STALE`, `BackfillSummary.stale`, `application.yml` (`auto-offset-reset: earliest`). Tests:
`IssueEventConsumerTest` (5), 2 more `IssueServiceTest`, 1 more real-DB test, and `KafkaErrorHandlingTest` (2) with
**real Kafka + Postgres containers** (`e2e/FullStackTest` base, shared with step 5).

### What it does
- `@KafkaListener(topics = "issue-events", groupId = "triage-worker")`: for each message, read the `issue` object,
  map it with the same `GitHubIssueMapper` the backfill uses, and call `IssueService.upsert`. labeled/unlabeled
  need nothing special: the issue object always contains its current labels.
- **Out-of-order safety:** `upsert` now only overwrites if `incoming.updated_at >= stored.updated_at`; otherwise it
  returns `STALE` and changes nothing. A redelivered "opened" from an hour ago can't reopen a closed issue or bring
  back removed labels. (Equal times do overwrite: that's the same data, or two changes in the same second, which
  arrive in order anyway because they share a partition.)
- **Errors** (`DefaultErrorHandler`):
  - a broken message (not JSON, no issue, mapper fails) -> `BadIssueEventException` -> **not retried** -> straight to
    `issue-events.DLT`;
  - anything else (e.g. the database blinked) -> retried **3 times** after 0.5 s, 1 s, 2 s -> then to the DLT.
  Either way the consumer moves on to the next message, so one bad message never blocks its partition.
- Checked on the real docker stack: group `triage-worker` was assigned partitions 0, 1, 2 and processed the two
  test messages from step 3 in order (`INSERTED`, then `UPDATED`). (The sample row was deleted afterwards.)

### Why at-least-once delivery is safe here
Kafka's consumer commits its position (the **offset**) *after* processing. If the app crashes after the upsert but
before the commit, the same message is delivered again after restart: **at least once**, sometimes twice. That's
fine because processing is **idempotent**:
1. the upsert matches on `(source, external_id)`, so the second time it updates the same row instead of adding one;
2. the data is the full issue state, not a change ("add label X"), so applying it twice gives the same row;
3. older data is ignored (`updated_at` rule), so even a re-delivery that arrives *after* a newer event is harmless.
"Exactly once" in Kafka needs transactions on both sides; idempotent processing gets the same result much more simply.

### Basics used here
- **`@KafkaListener`**: Spring calls this method for every message on the topic. Spring Boot's listener container
  polls Kafka, calls the method, commits the offset, and on an exception hands the message to the error handler.
  *Before:* write a `while (true) { consumer.poll(...); for each record ...; consumer.commitSync(); }` loop yourself.
  *After:* `@KafkaListener(topics = "issue-events", groupId = "triage-worker") void onIssueEvent(ConsumerRecord<String,String> r)`.
- **`ConsumerRecord`**: one message plus where it came from: `key()`, `value()`, `partition()`, `offset()`.
- **`DefaultErrorHandler` + `ExponentialBackOffWithMaxRetries(3)`**: retry the failed message in the same consumer,
  waiting longer each time; after the last retry, call the "recoverer".
- **`DeadLetterPublishingRecoverer`**: the recoverer that sends the failed message to another topic (here
  `issue-events.DLT`, same partition) with headers explaining why (`kafka_dlt-exception-cause-fqcn`, message, stack trace).
- **`addNotRetryableExceptions(BadIssueEventException.class)`**: skip the retries for errors that can't fix themselves.
- **`auto-offset-reset: earliest`**: what a *new* consumer group does when it has no saved position: start at the
  oldest message (instead of only new ones), so nothing sent before the worker first started is lost.
- **`@SpringBootTest` + Testcontainers Kafka/Postgres**: the whole app against real infrastructure. `@MockitoSpyBean`
  wraps the real `IssueService` so a test can make *one* call fail (`doThrow(...).doCallRealMethod()`) and prove the
  retry works. Waiting uses a plain loop (check every 100 ms, give up after 10 s); no extra library.

### One alternative I rejected
**Spring Kafka's `@RetryableTopic`** (non-blocking retries: failed messages go to `issue-events-retry-0`, `-retry-1`...
topics and come back later). It doesn't hold up the partition while waiting, but it **breaks ordering** (a retried
"opened" could be applied after a newer "closed"), needs more topics, and our STALE rule would then be doing a lot of
work. Blocking retries of a few seconds keep events in order and are simpler; a broken message still leaves quickly.

### Likely interview questions
1. **What happens if the consumer crashes after writing to the database but before committing the offset?**
   The message is delivered again after restart (at-least-once). The upsert is idempotent and ignores older data, so
   the second run changes nothing.
2. **How does a poison message not block the whole partition?**
   Messages that can't be parsed or mapped throw a non-retryable exception and go straight to the DLT; other errors are
   retried 3 times with backoff and then also go to the DLT. Either way the consumer commits and continues. A test sends
   a bad message and then a good one with the same key: the good one is stored, the bad one is on the DLT.
3. **Events for an issue arrive out of order. How do you avoid old data overwriting new?**
   Same key -> same partition keeps them ordered in normal operation. For the rest (redeliveries, backfill racing a
   webhook), the upsert compares `updated_at` and ignores anything older than what's stored.

- **`@SpringBootTest(webEnvironment = RANDOM_PORT)` + `@LocalServerPort`:** starts the real web server on a free port
  and tells the test which one, so tests never clash with an app already running on 8080.
- **`java.net.http.HttpClient`** (JDK): sends real HTTP requests. Unlike Spring's `RestClient`, it doesn't throw on 401,
  so the test can simply check `statusCode()`.
- **Polling instead of sleeping:** the consumer is asynchronous, so the test checks the DB every 100 ms up to 10 s
  (`waitUntil`). A fixed `Thread.sleep(5000)` would be both slower and flaky.
- **Proving "nothing happened":** you can't wait for an absence, so the test reads the topic for a fixed 3 s and

### One alternative I rejected
**Spring Kafka's embedded broker (`@EmbeddedKafka`)**. It's lighter, but it needs `spring-kafka-test` (not on the
approved list) and runs a Kafka inside the JVM that isn't the image we run in docker-compose. Testcontainers runs the
same `apache/kafka:4.1.0` image, and Postgres 16, as development does. Also rejected: Awaitility for the polling
(a new dependency for a 10-line loop).

### Likely interview questions
1. **How do you test an asynchronous flow (HTTP -> Kafka -> consumer -> DB) reliably?**
   Real containers for Kafka and Postgres, post a real signed request, then poll the database with a timeout instead of
   sleeping a fixed time. Absence ("nothing was published") is checked by reading the topic for a fixed short window.
2. **What does your E2E test prove that unit tests don't?**
   That the pieces are wired together: the right topic and key, the consumer group really receives the message, the JSON

3. **How fast does the webhook receiver answer, and why does it matter?**
   About 76 ms in the test (verify, insert delivery row, publish and wait for the Kafka ack). GitHub stops waiting after
   10 s and marks the delivery as failed, so the slow work (mapping, DB upsert, later triage) happens in the consumer.

## M3 step 0: deleted and transferred issues (4 Nov 2026)

Files: `GitHubWebhookController.HANDLED_ACTIONS` (+ deleted, transferred), `IssueService.delete`,
`IssueEventConsumer` (REMOVING_ACTIONS). Tests: 2 consumer unit tests, 1 real-DB test, 2 end-to-end tests.

### What it does
- `issues/deleted`: the issue is gone on GitHub, so the worker removes our row, matched by `(source, external_id)` =
  `issue.id`. Its labels go with it.
- `issues/transferred`: the issue moved to another repo. GitHub sends the **old** issue as `issue` and the new one
  (new id, new number, new repo) under `changes.new_issue` / `changes.new_repository`. We remove the old repo's row.
  (If we also watch the new repo, its own webhook brings the new issue in.)
- Removing a row that's already gone returns false and does nothing, so a repeated message is harmless.

### Basics used here
- **`repository.delete(entity)`** (JPA): Hibernate first deletes the `@ElementCollection` rows (`issue_label`),
  then the `issue` row. The database's `ON DELETE CASCADE` on `issue_label.issue_id` would also remove them if
  something deleted the row with plain SQL. Two safety nets.
  *Before:* `DELETE FROM issue_label WHERE issue_id = ?; DELETE FROM issue WHERE id = ?` by hand.
  *After:* find by key, `issueRepository.delete(row)`.
- **Same pipeline, different action:** the receiver doesn't care what the action means; the consumer branches on it.
  That keeps the 10-second path the same for every event.

### One alternative I rejected
**A "deleted" flag (soft delete) instead of removing the row.** It keeps history and protects against a late `edited`
event re-creating the row, but every query would need `WHERE NOT deleted`, and sai asked for removal. Known gap: an
`edited` event delivered *after* `deleted` (very unlikely: same partition, so in order) would re-insert the issue.

### Likely interview questions
1. **How do you handle an issue being deleted or moved?**
   The webhook's `deleted` / `transferred` action removes our row by the tracker's issue id; labels cascade. Transfers
   carry the old issue in `issue` and the new one in `changes.new_issue`.
2. **What if the delete event is processed twice?**
   The second delete finds nothing and returns false: idempotent like the upsert.
3. **Hard delete or soft delete?**
   Hard delete here: simpler queries, and we don't need history of deleted issues. Soft delete would keep an audit
   trail and block late events from resurrecting the row, at the cost of a filter on every query.

## M3 step 1: pgvector (4 Nov 2026)

Files: `docker-compose.yml` (`pgvector/pgvector:pg16-trixie`), `V4__pgvector_issue_embedding.sql`, Testcontainers on
the same image, docs/schema.md; test `PgvectorSchemaDbTest` (3).

### What it does
- The Postgres container now runs an image that is the official Postgres 16 **plus the pgvector extension**. Same
  major version and same Docker volume, so the data stayed: before and after, 44,205 issues (43,810 spring-boot + 394
  petclinic + 1 sandbox), 54,668 labels, 1,036 `duplicate_of`.
- V4: `CREATE EXTENSION vector`, table `issue_embedding(issue_id PK/FK ON DELETE CASCADE, model, embedding vector(384),
  created_at)`, and an **HNSW** index with `vector_cosine_ops`. pgvector version 0.8.7.

### The gotcha: collation versions
The first try used `pgvector/pgvector:pg16`. Postgres warned: *"database triage has a collation version mismatch:
created using 2.41, the OS provides 2.36"*. Text sorting comes from the C library (glibc) of the OS image: `postgres:16`
is Debian 13 (glibc 2.41), the plain `pg16` pgvector tag is Debian 12 (glibc 2.36). If sort rules differ, B-tree indexes
on text columns (our unique key, the label indexes) can silently become wrong. Fix: use `pg16-trixie` (Debian 13,
glibc 2.41, same as before). Nothing had written to the DB in between, so no REINDEX was needed; otherwise the fix is
`REINDEX DATABASE triage; ALTER DATABASE triage REFRESH COLLATION VERSION;`.

### Basics used here
- **Embedding**: a list of numbers (here 384) that represents the meaning of a text; texts that mean similar things get
  vectors pointing in similar directions. *Before:* compare issues by shared words. *After:* compare their vectors.
- **Cosine distance** (`<=>` in pgvector): 0 = same direction (very similar), 1 = unrelated, 2 = opposite.
  Similarity = 1 - distance. The test checks exactly that: same vector -> 0, negated vector -> 2.
- **`vector(384)`**: a column type from pgvector; written as text like `'[0.1,0.2,...]'::vector`.
- **HNSW index** (Hierarchical Navigable Small World): a graph where each vector links to near neighbours, in layers
  (few long links on top, many short ones below). A search walks the graph instead of comparing with every row:
  much faster, slightly approximate. `vector_cosine_ops` builds it for cosine distance.
- **`ON DELETE CASCADE`** on `issue_embedding.issue_id`: deleting an issue (e.g. the `deleted` webhook) removes its vector.
- **`asCompatibleSubstituteFor("postgres")`** (Testcontainers): "this image behaves like the official postgres image",
  so the Postgres module accepts it.

### One alternative I rejected
**A separate vector database** (Qdrant, Pinecone, Weaviate). Another service to run and keep in sync with Postgres,
for 44k vectors that Postgres handles easily. With pgvector the vectors sit next to the issues, so "same repo, created
before X" filters and joins are plain SQL, in one transaction, with one backup.

### Likely interview questions
1. **Why pgvector instead of a dedicated vector database?**
   Tens of thousands of vectors, filters on normal columns (repo, created_at), and one database to run and back up.
   pgvector gives an HNSW index and SQL joins; a separate store would need syncing and adds an operational piece.
2. **What is an HNSW index?**
   An approximate nearest-neighbour index: a multi-layer graph of vectors linked to near neighbours. Searches walk it
   from coarse to fine layers, visiting a small part of the data. Trade-off: speed vs a little recall (tunable with `ef_search`).
3. **You changed the Postgres image under existing data. What could go wrong?**
   A different major version can't read the files (we kept 16). A different OS can change text collation, which can
   corrupt text indexes: Postgres warned about it, and the fix was an image on the same Debian release (or REINDEX).

## M3 step 2: keyword baseline with Postgres full-text search (4 Nov 2026)

Files: `V5__issue_full_text_search.sql`, `triage/DuplicateSearch.java` (interface), `triage/SimilarIssue.java`,
`triage/KeywordDuplicateSearch.java`; test `KeywordDuplicateSearchDbTest` (4, real Postgres).

### What it does
- V5 adds `issue.search_tsv`, a **generated** `tsvector` column: title (weight A) + first 2,000 characters of the body
  (weight B) with HTML comments removed, English stemming. A GIN index makes matching fast. Applied to 44k rows in 3.1 s.
- `KeywordDuplicateSearch.findSimilar(issueId, 3)`: take the query issue's own lexemes, join them with OR into a
  `tsquery`, match earlier issues of the same repo, rank with `ts_rank`, return the top k (number, title, score).
  About 115 ms per query on spring-boot.
- Both searches (this and the vector one in step 4) implement `DuplicateSearch` with the same rule: **same repo,
  created before the query issue**, never the issue itself. That is what a maintainer could have found at the time.

### Basics used here
- **`tsvector`**: a text turned into a sorted list of normalised words ("lexemes") with positions: `to_tsvector('english',
  'Health endpoints returning 404')` -> `'404':4 'endpoint':2 'health':1 'return':3`. Stop words ("the", "is") are dropped and
  words are stemmed ("returning" -> "return"), so different forms of a word match.
- **`tsquery` and `@@`**: a search expression (`'health' | 'endpoint'` = OR, `&` = AND); `doc @@ query` is true if it matches.
  *Before:* `WHERE title ILIKE '%health%'` (one word, no stemming, no ranking, no index). *After:* `search_tsv @@ query`, ranked.
- **`ts_rank`**: a relevance score: higher when more query words appear, more often, and in heavier-weighted parts
  (`setweight(..., 'A')` = the title counts most).
- **Generated column (`GENERATED ALWAYS AS (...) STORED`)**: Postgres computes and stores it on every insert/update.
  Our Java code never writes it, and Hibernate's `validate` ignores columns the entity doesn't map.
- **GIN index**: an inverted index: word -> rows containing it. The right index for `@@`.
- **Why OR, not AND:** `plainto_tsquery` ANDs every word, so a 150-word issue would only match itself. OR + ranking
  rewards the issues sharing the most (and the most important) words.
- **Quoting lexemes:** each lexeme is wrapped in quotes with `'` and `\` escaped before the `::tsquery` cast; a test uses
  `C:\temp\app isn't` to prove odd characters don't break the query.

### One alternative I rejected
**Elasticsearch/OpenSearch (BM25)** as the keyword baseline. A better-tuned text ranker, but a whole new service. The
point of the baseline is "what plain keyword search already gets you", and Postgres full-text search is that, in the
database we already have. (Also rejected: building the query from the title only. Fairer to give both methods the same text.)

### Likely interview questions
1. **How does your keyword baseline work?**
   Postgres full-text search: a generated, GIN-indexed `tsvector` over title + body; the query issue's lexemes ORed into a
   `tsquery`; earlier issues of the same repo ranked by `ts_rank`. Same text window and same "earlier, same repo" rule as the vector search.
2. **Why do you need a baseline at all?**
   "Vector search finds 60% of duplicates" means nothing alone. Against keyword search on the same data and rule, it says
   how much the embeddings actually add. Maintainers already have keyword search (GitHub's search box).
3. **Why only issues created before the query issue?**
   That's what was knowable when the issue was opened. Searching later issues would let the original's *own* duplicates or
   later discussion leak into the result: an evaluation that looks better than reality.

## M3 step 3: embeddings with all-MiniLM-L6-v2, in-process (4 Nov 2026)

Files: `pom.xml` (LangChain4j BOM 1.22.0, `langchain4j-core`, `langchain4j-embeddings-all-minilm-l6-v2`),
`embedding/EmbeddingService.java` (our interface), `MiniLmEmbeddingService.java`, `EmbeddingText.java`,
`IssueEmbeddingRepository.java`, `IssueEmbeddingService.java`, `web/EmbeddingController.java`
(`POST /embeddings/{owner}/{repo}`); the Kafka worker embeds new and changed issues. Tests: `EmbeddingTextTest` (3),
`MiniLmEmbeddingServiceTest` (3, real model), `IssueEmbeddingServiceTest` (3), `IssueEmbeddingRepositoryDbTest` (4, real
pgvector), 1 more consumer test, and the end-to-end test now checks the embedding row.

### What it does
- **Text** per issue: title + first 2,000 characters of the body, HTML comments removed, whitespace collapsed
  (`EmbeddingText`): the same window as the keyword search.
- **Model**: all-MiniLM-L6-v2 (384 numbers per text), run **inside the JVM** with ONNX Runtime; the model file is in the
  LangChain4j jar. No API key, no network, no cost per call.
- **Batch job** `POST /embeddings/{owner}/{repo}`: finds issues with no embedding from the current model, 256 at a time,
  embeds them with `embedAll`, saves with one `batchUpdate` (`INSERT ... ?::vector ... ON CONFLICT DO UPDATE`), logs
  progress, returns `{repo, model, embedded, durationMs}`. Re-running only embeds what's missing. Real runs:
  spring-petclinic 394 issues in 2.2 s; spring-boot **43,810 issues in 333 s** (5.5 min, ~130 issues/s on a laptop CPU).
- **Live**: after the Kafka worker inserts or updates an issue (not when STALE), it re-embeds it.

### Basics used here
- **Sentence-embedding model**: a small neural network trained so that sentences with similar meaning get vectors with
  high cosine similarity. "port 8080 already in use" and "web server can't bind, port taken" share almost no words but
  come out close; the test checks they are closer than an unrelated YAML issue.
- **ONNX Runtime**: runs a trained model (exported to the ONNX format) on the CPU from Java. *Before:* call an embeddings
  API over HTTP per issue (a key, network, cost, rate limits). *After:* `model.embed(text)` in-process, ~180 texts/second.
- **Our own interface (`EmbeddingService`)**: callers depend on `embed(text)`, not on LangChain4j. Changing the model
  (another local one, or an API) is one new class; `model` is stored with each vector, so `countMissing` then shows
  everything needs re-embedding.
- **`?::vector`**: the JDBC driver doesn't know pgvector's type, so we send text `"[0.1,-0.2,...]"` and cast it in SQL.
- **`jdbc.batchUpdate(sql, rows)`**: sends many inserts in one round trip.
- **Why no LangChain4j Spring Boot starter**: its auto-configuration targets particular Spring Boot versions; creating
  `new AllMiniLmL6V2EmbeddingModel()` in our own `@Component` works with any Boot version and is one line.

### One alternative I rejected
**An embeddings API (OpenAI, Voyage, Cohere).** Better models, but every issue costs a network call and money, needs a
key, and the 44k-issue backfill would hit rate limits. The local model is free, private and fast enough; the interface
makes a later switch cheap if the evaluation (step 6) shows we need a stronger model.

### Likely interview questions
1. **How do you compute embeddings, and why locally?**
   all-MiniLM-L6-v2 via LangChain4j + ONNX Runtime inside the JVM: 384-dim vectors, no key, no per-call cost, no data
   leaving the machine. Behind our own `EmbeddingService` interface so the model can change.
2. **How do you keep embeddings up to date?**
   A batch job embeds whatever is missing for the current model (resumable, idempotent), and the Kafka worker re-embeds an
   issue whenever its text changes. Deleted issues lose their vector through `ON DELETE CASCADE`.
3. **What text do you embed and why?**
   Title + first 2,000 characters of the body without template comments: the title carries most meaning, the start of
   the body has the symptom; long logs at the end add noise (and the model only reads ~256 tokens well anyway).

## M3 step 4: vector top 3 with pgvector (4 Nov 2026)

Files: `triage/VectorDuplicateSearch.java`, `triage/SimilarIssueService.java`, `web/SimilarIssueController.java`
(`GET /repos/{owner}/{repo}/issues/{number}/similar?method=vector|keyword&limit=3`); tests `VectorDuplicateSearchDbTest`
(4, real pgvector, hand-made vectors), `SimilarIssueControllerTest` (4).

### What it does
- Two queries: (1) the issue's own vector, repo and `created_at`; (2) the nearest **earlier** issues of the **same repo** by
  cosine distance, `ORDER BY embedding <=> ?::vector LIMIT k`, returning number, title and score (= 1 - distance).
- Real example, spring-boot #52529 (answer key: duplicate of #52519): **vector top-1 = #52519** "Support
  MockServerConnectionDetails on DockerComposeService", score 0.807. Keyword top 3 = three other Docker issues; #52519
  isn't among them.
- `EXPLAIN ANALYZE`: `Index Scan using idx_issue_embedding_hnsw`, **6 ms** on 43,810 vectors.

### The HNSW + filter problem, and how it's handled
An HNSW index answers "the nearest vectors"; the `WHERE` (same repo, created before) is applied **after**. If the nearest
40 (the default `ef_search`) are all from another repo or newer, a plain index scan returns *fewer than k rows* and no
error. pgvector 0.8's **iterative index scan** fixes that: `SET LOCAL hnsw.iterative_scan = strict_order` keeps walking the
index until enough rows pass the filter, still in exact distance order. `ef_search = 100` widens each step (better recall).
`SET LOCAL` = only for this transaction, which is why the method is `@Transactional`. A test proves it: 40 nearer vectors
from another repo, the index forced on (`enable_seqscan = off`), and the 3 results are still the right 3 from our repo.

### Basics used here
- **Nearest-neighbour query in SQL**: `ORDER BY embedding <=> :query LIMIT 3`: "sort by distance to the query, keep 3".
  With an HNSW index Postgres walks the graph instead of computing all 43,810 distances.
- **Pass the vector as a parameter, not a join**: the index can only be used when the thing being compared against is a
  fixed value for the query, so we read the issue's vector first and send it back as `?::vector`.
- **`List<DuplicateSearch>` injection**: Spring passes *every* bean that implements the interface; the service turns them
  into a map by `name()` ("keyword", "vector"), so `?method=` picks one and a third search is just a new `@Component`.
- **`EXPLAIN ANALYZE`**: shows the plan Postgres really used and how long each step took.

### One alternative I rejected
**Exact search (no index, compare with every row).** 43k vectors is small enough that a full scan takes tens of ms, and it's
always exact. But it grows linearly with the data, and the prompt asks for the HNSW index; with iterative scans the index
gives the same top results for this data at a fraction of the cost. (Also rejected: IVFFlat, pgvector's other index; it
needs training on existing data and re-tuning as data grows, while HNSW works well from the first row.)

### Likely interview questions
1. **How do you find similar issues fast?**
   Embeddings in pgvector with an HNSW index (cosine). Query = the issue's vector as a parameter, `ORDER BY <=> LIMIT 3`,
   filtered to the same repo and earlier issues. ~6 ms on 44k vectors.
2. **What goes wrong when you filter an approximate nearest-neighbour search?**
   The index returns its nearest candidates first and the filter removes some, so you can silently get fewer results.
   pgvector 0.8 iterative scans keep scanning until the limit is filled; a test forces the index and checks it.
3. **Cosine similarity vs Euclidean distance?**
   Cosine compares direction only (meaning), not length; sentence-embedding models are trained for it. `<=>` is cosine
   distance in pgvector; similarity = 1 - distance.

## M3 step 5: label suggestion by weighted vote (4 Nov 2026)

Files: `triage/LabelSuggester.java`, `SimilarIssueService.suggestLabels`, endpoint
`GET /repos/{owner}/{repo}/issues/{number}/labels/suggested`, `application.yml` (`triage.labels.*`);
test `LabelSuggesterDbTest` (3, real pgvector).

### What it does
1. Take the **10 nearest earlier issues** of the same repo (the vector search's neighbours, with our ids).
2. Each neighbour votes for each of its labels with its similarity as the weight.
3. A label's **share** = its votes / the total weight of all 10 neighbours. Suggest it if share >= **0.5**
   ("issues holding more than half of the similarity agree").
4. Workflow labels (prefix `status:`, e.g. `status: waiting-for-triage`, `status: duplicate`) are never suggested: they
   say where an issue is in the process, not what it is about. Both settings are in `application.yml`.
Real examples: #52591 -> `type: bug` (share 0.63; it really is `type: bug`). #52519 -> nothing (its only label is
`status: declined`, a workflow label).

### Basics used here
- **k-nearest-neighbour (kNN) classification**: "label a new thing like its most similar known things". No training step:
  the "model" is the labelled history plus the embeddings.
- **Weighted vote**: a neighbour with similarity 0.95 counts more than one with 0.40, so a few very similar issues beat
  many vaguely related ones. *Before (plain majority):* 6 of 10 neighbours are `type: bug` -> bug. *After:* those 6 must
  also carry more than half of the total similarity.
- **Threshold**: only speak when the neighbours mostly agree; otherwise suggest nothing (better silent than noisy).
- **`= ANY (?)` with a `Long[]`**: one query for the labels of all 10 neighbours instead of 10 queries.
- **`@Value("${triage.labels.ignore-prefixes:status:}") List<String>`**: Spring splits a comma-separated property into a list;
  after the first `:` comes the default value.

### One alternative I rejected
**Training a classifier** (e.g. logistic regression on the embeddings, one per label). Could be more accurate, but needs
a training pipeline, retraining when labels change, and a model to version and explain. kNN voting works from the data we
already have, adapts immediately when maintainers relabel issues, and each suggestion can be explained ("7 of the 10 most
similar issues were `type: bug`").

### Likely interview questions
1. **How do you suggest labels?**
   kNN: the 10 most similar earlier issues vote for their labels, weighted by similarity; a label is suggested only if it
   gets at least half of the total weight. Workflow labels like `status:` are excluded.
2. **Why a threshold instead of always suggesting the top label?**
   A wrong suggestion costs a maintainer's attention and trust. When neighbours disagree, staying silent is better; the
   evaluation (step 6) reports both precision and how often we make a suggestion at all (coverage).
3. **How would this behave on a brand-new repo?**
   With few earlier issues there are few neighbours and weak agreement, so mostly no suggestions: it gets useful as
   labelled history grows. Starting from a related repo's data (or a trained model) would help the cold start.

- **False alarms** on 1,000 random non-duplicates **from external reporters**: the threshold for <= 10% false alarms is
  cosine 0.825; at it, the original is top-1 (and flagged) for 10.8% of duplicates, in the top 3 for 13.6%.
- **Labels** on the 1,000 most recent external issues with a real label: a suggestion for 30.6%, top label right 69.3%.

### What the data taught (and the fix)
The first run used *all* issues for false alarms and got a threshold of **0.998**: 10% of random non-duplicates had an
almost identical earlier issue. They were the spring-boot team's bookkeeping issues: **6,964 forward-port clones** (the
same issue copied to another branch) and **12,768 "Upgrade to X"** dependency issues, all opened by team members. A triage
assistant never triages those; it looks at issues from people outside the team. So false alarms and labels are now
measured on **external reporters** (`author_association` not OWNER/MEMBER/COLLABORATOR), and the all-issues numbers are
still reported next to them (labels on all issues: 85.5% precision, inflated by easy "dependency-upgrade" cases).

### Basics used here
- **recall@k**: share of duplicates whose true original is in the top k results. recall@3 = "a maintainer looking at our
  top 3 would see the right issue".
- **MRR (mean reciprocal rank)**: average of 1/rank (1st -> 1, 2nd -> 0.5, 3rd -> 0.33, not in top 10 -> 0). One number that
  rewards ranking the original high.
- **False-alarm rate**: of issues that are NOT duplicates, how many we'd still flag. Choosing the threshold on non-duplicates
  (here the 90th percentile of their top-1 scores) and then reading recall at it is the honest way to set an operating point.
- **Time-ordered replay**: only use what was knowable at the time (earlier issues), otherwise the evaluation leaks the future.
- **Repeatable random sample**: `ORDER BY md5(id || 'seed')` gives the same "random" 1,000 every run.

### One alternative I rejected
**Reporting only recall@k** (the flattering 46%/61%). Without false alarms it hides that similar-but-not-duplicate issues
are common: at a 10% false-alarm budget only 13.6% of duplicates get a confident, correct flag. That's why the default
output stays a private top-3 (shadow mode) and a public comment needs a high threshold.

### Likely interview questions
1. **How good is your duplicate detection?**
   Time-ordered replay over 833 maintainer-confirmed spring-boot duplicates: the original is in our top 3 for 46.2% (vs
   26.5% for keyword search) and top 10 for 60.9%; MRR 0.403 vs 0.244. At a threshold with 10% false alarms on external
   issues, 13.6% get a confident correct flag, so we show a private top-3 rather than auto-commenting.
2. **How did you avoid fooling yourself in the evaluation?**
   Answer key from GitHub's own records (strict rules, spot-checked); only earlier issues searched; pairs whose original is
   newer or not an issue excluded and counted; false alarms measured on the population the bot really sees; the same text
   window for both methods; a repeatable sample.
3. **What surprised you?**
   Over 40% of spring-boot's issues are team bookkeeping clones (forward-ports, dependency upgrades) with near-identical
   twins: they pushed the false-alarm threshold to 0.998 until I measured on external reporters only.

## M4 step 0: per-repo candidate filter (4 Nov 2026)

Files: `triage/CandidateFilter.java`, `triage/CandidateFilterProperties.java`, both searches (`KeywordDuplicateSearch`,
`VectorDuplicateSearch`), `DuplicateSearch` (new 3-argument `findSimilar`), `EvalService`/`EvalReport`/`MarkdownReport`
(recall with and without the filter), `application.yml` (`triage.candidates.exclude-labels`); tests `CandidateFilterTest` (3),
`VectorDuplicateSearchTest` (1), one new case each in `KeywordDuplicateSearchDbTest` and `VectorDuplicateSearchDbTest`.

### What it does
sai's M3 decision 2: a per-repo list of labels whose issues are never returned as duplicate candidates, in config, with
nothing spring-boot-specific in the code. For spring-boot it lists `status: forward-port` (the team's per-branch clone of an
issue). Both searches add `AND NOT EXISTS (... label_name = ANY (?))`; the eval runs every search with and without it.

### The result (honest: the idea didn't work)
| | recall@1 | recall@3 | recall@10 | MRR |
|---|---|---|---|---|
| vector, no filter (M3) | 31.0% | **46.2%** | 60.9% | 0.403 |
| vector, with filter | 30.1% | 45.6% | 59.9% | 0.396 |

Why: in 13 scored pairs the maintainer's "original" **is** a forward-port clone, and 8 of them were in the top 3 without the
filter (rank 1 for 7). The filter makes those impossible to find. The gain it was meant to bring (a clone pushing the real
original down) happened only 0/3/1 times at top 1/3/10. So the clones weren't the problem. Recommendation: keep the
mechanism, remove the spring-boot entry from config. Labels don't use the filter: a clone has the same labels as its
original, so it is fair evidence.

### A bug the re-run found: @Transactional and self-invocation
The first re-run gave 35 of 1,000 false-alarm samples **no result at all**. Cause: `DuplicateSearch.findSimilar(id, limit)`
became an interface default method without `@Transactional`. Spring adds transactions with a **proxy**: a wrapper object
that starts a transaction and then calls the real object. A call from *inside* the real object (`this.findSimilar(...)`)
never passes the proxy, so it gets no transaction of its own.
- Before (broken): proxy.findSimilar(id, 3) → no annotation → no transaction → real.findSimilar(id, 3, true) (`this` call)
  → `SET LOCAL hnsw.iterative_scan` outside a transaction does nothing → HNSW stops after ~40 candidates, the filters
  remove them all → `[]`.
- After: `VectorDuplicateSearch` overrides the 2-argument method just to put `@Transactional(readOnly = true)` on it. A unit
  test asks Spring's `AnnotationTransactionAttributeSource` whether each public search method is transactional.
Recall was never affected (the eval called the annotated 3-argument method); the false-alarm and threshold numbers were.

### Basics used here
- **`@ConfigurationProperties(prefix = "triage.candidates")`** on a record: Spring copies matching YAML keys into the record's
  fields (`exclude-labels` → `excludeLabels`). Before: many `@Value("${...}")` strings; after: one typed object. It is
  registered with `@EnableConfigurationProperties(CandidateFilterProperties.class)` on the bean that uses it.
- **Map keys with "/"** in YAML need brackets: `"[spring-projects/spring-boot]"`, otherwise Spring drops the slash.
- **`= ANY (?)`** with a Java `String[]` parameter: the Postgres driver sends it as `text[]`; an empty array matches nothing,
  so "no labels configured" needs no special SQL.

### One alternative I rejected
**Merging clones into their original** (one group per problem, any member counts as a hit). It would fix both directions,
but needs a reliable clone→original link (the clone's body links it only by text); too much for a filter that turned out to
matter in under 1% of pairs.

### Likely interview questions
1. **You added a filter and recall went down. Why keep it?** The mechanism is generic and cheap (a config list); the data
   showed this particular label is the wrong one to exclude for spring-boot, so I recommended removing that entry. Measuring
   before trusting an idea is the point.
2. **Why did your vector search return nothing for some issues?** `@Transactional` works through a proxy; a self-call skipped
   it, so `SET LOCAL` (pgvector's iterative scan) had no effect and HNSW's ~40 candidates were all filtered out. Fixed by
   annotating the entry method and testing that every public search method is transactional.
3. **How do you configure per-tenant behaviour in Spring Boot?** A `@ConfigurationProperties` record with a map keyed by
   tenant (repo), normalised to lower case, with an empty default so unknown tenants get the normal behaviour.

## M4 step 1: TriageLlm, the fake LLM and versioned prompt files (4 Nov 2026)

### What it does
- **`TriageLlm`** is our own two-method interface: `model()` and `complete(Prompt) -> LlmReply(text, inputTokens,
  outputTokens)`. Every LLM feature (missing details, duplicate check, draft reply) talks only to this.
- **`FakeTriageLlm`** answers with simple rules per prompt name, estimates tokens as characters / 4, and costs nothing. Tests

**LangChain4j's `@AiService` interfaces** (declare a Java interface, LangChain4j generates the LLM call and JSON parsing).

### Likely interview questions
1. **How do you test code that calls an LLM?** Behind our own interface; unit tests use a fake with fixed answers (including

2. **Why version prompts by file name?** A prompt change changes the output like a code change does. Storing

## M4 step 2: missing-details check with strict JSON (4 Nov 2026)

Files: `prompts/missing-details-v1.txt`, `ai/MissingDetailsChecker.java`, `ai/MissingDetails.java`, `ai/StrictJson.java`,
a keyword rule in `FakeTriageLlm`; tests `MissingDetailsCheckerTest` (9) with a `ScriptedTriageLlm` test helper.

### What it does
For a new issue, the LLM says for each of **version, steps to reproduce, expected vs actual, logs/stack trace** whether it is
`present`, `missing` or `not_applicable` (e.g. steps for a feature request). The answer must be exactly one JSON object with
exactly those four keys and allowed values. Bad answer → ask once more → still bad (or the call failed) → status `UNKNOWN`
with the reason, never a guess. Bodies are cut at 6,000 characters. The result keeps the prompt version and tokens used.

### Basics used here
- **Validate LLM output like user input.** The model can add "Sure! Here's the JSON:", drop a key or invent a value. Before:
  `mapper.readValue(answer, Map.class)` and hope. After: parse, check the exact key set, check each value against an enum,
  and only then use it.
- **One leniency on purpose**: a Markdown code fence (```json ... ```) is removed; models add it often and it doesn't
  change the meaning. Anything else around the JSON is rejected.
- **`EnumMap`**: a map whose keys are enum values, kept in the enum's order; fast and readable.
- **Jackson 3** (`tools.jackson...`): Spring Boot 4's JSON library. `JacksonException` is unchecked now, and
  `propertyNames()` lists an object's keys.

### One alternative I rejected
**The provider's "structured output" / tool-calling mode** (the API forces a JSON schema). Worth trying with the real model
at STOP A, but the parser and the retry must exist anyway (another provider may not support it, and the fake doesn't), and
they're what's tested here.

### Likely interview questions
1. **What if the LLM returns invalid JSON?** Strict parse and validation; one retry; then "unknown" with the reason, shown as
   such in the report. Both calls' tokens are counted.
2. **Why "not_applicable" as a third value?** Without it the model must call steps-to-reproduce "missing" for a feature
   request, and the bot would ask reporters for nonsense.
3. **Why not regexes instead of an LLM?** The fake LLM *is* regexes, and it's easy to fool ("expected" in "unexpected
   error"). An LLM understands "here's my pom.xml with 3.4.1" as a version. The real comparison comes from the STOP A hand-scoring.

## M4 step 3: "already fixed?" hint, without an LLM (4 Nov 2026)

Files: Flyway `V6__issue_fix.sql`, `source/FixInfo.java`, `source/FixSource.java`, `github/GitHubFixSource.java` (GraphQL),
`triage/Version.java`, `triage/ReporterVersion.java`, `triage/IssueFixRepository.java`, `triage/FixedHint.java`,
`triage/FixedHintService.java`; tests `VersionTest` (2), `ReporterVersionTest` (2), `GitHubFixSourceTest` (5),

### What it does
If the top duplicate match is **closed as completed**, find the version its fix shipped in, and compare it with the version
the new issue's reporter uses:
- **Fix version**: GitHub GraphQL `ClosedEvent.closer` (a PR or a commit). The closing PR's milestone wins, else the issue's

### One alternative I rejected
**Asking the LLM "is this already fixed?"** It would guess from text. GitHub's records (closer + milestone) are facts, cost

2. **What if the reporter didn't say their version?** The hint says "fixed in X, ask for their version". The missing-details

3. **Why not hint on issues closed as "not planned"?** Nothing was fixed there. Telling the reporter to upgrade would be wrong.

## M4 step 4: RAG draft reply from spring-boot's reference docs (4 Nov 2026)

Files: Flyway `V7__doc_chunk.sql`; package `docs`: `DocsProperties`, `DocSource` + `GitHubDocSource`, `AsciidocChunker`,
`DocSection`, `DocChunkRepository`, `DocIngestService`; `web/DocsController` (`POST /docs/{o}/{r}`, `GET /docs/{o}/{r}/search?q=`);
`prompts/draft-reply-v1.txt`, `ai/DraftReplyService`, `ai/DraftReply`; tests `AsciidocChunkerTest` (5), `DocIngestServiceTest` (2),
`GitHubDocSourceTest` (3), `DocChunkRepositoryDbTest` (1), `DraftReplyServiceTest` (5).

### What it does
1. **Load**: GitHub's git-trees API lists every file of spring-boot at tag **v4.1.2** (one call). The Antora pages of the
   `ROOT`, `reference` and `how-to` modules are read from raw.githubusercontent.com: 123 pages.
2. **Chunk**: cut at headings. Each piece keeps its heading path ("SQL Databases > Embedded Database Support") and its
   published URL with the section's `#anchor` (from the `[[id]]` line before the heading). Long sections are split into
   ≤ 1,200-character pieces with a 200-character overlap: **1,318 chunks**. Docs macros become plain text, code blocks stay.
3. **Embed + store**: the same MiniLM model as the issues, in `doc_chunk` with an HNSW index. The whole load takes 13 s and
   replaces the repo's chunks in one transaction.
4. **Draft**: the 5 nearest chunks (cosine ≥ 0.55) and the 3 most similar earlier issues (≥ 0.75) become numbered sources.
   The LLM writes ≤ 120 words citing their URLs. **No source above the thresholds → no LLM call, status NOTHING_RELEVANT.**
   Links in the draft that aren't sources are listed in `unknownLinks` as a warning.

### Choices made from the data
- **1,200 characters, not ~500 tokens**: MiniLM reads only the first 256 word pieces. Longer chunks would be cut off by the
  model, so their ends would never be found.
- **Threshold 0.55**: on the 300 most recent external issues, the best docs score is 0.42 at p10, 0.59 at the median and 0.71
  at p90. So 65% of issues get docs sources. A starting point, to check with the hand-scoring at STOP A.
- **`exclude-pages: ROOT/redirect`**: that page is only a list of old anchors; it was the top hit for many queries.
- **Retries**: raw downloads failed twice in a row on a network blip (closed connection, failed DNS lookup), so each file gets 3 tries.

### Basics used here
- **RAG (retrieval-augmented generation)**: before: ask the LLM "answer this issue" and it answers from memory, maybe wrongly
  or for an old version. After: find the relevant docs sections first, give them to the LLM, and tell it to use only those
  and cite them. The answer is checkable and tied to a version (the tag).
- **Chunk overlap**: a sentence cut in half at a chunk border still exists whole in one of the two chunks.
- **Token scope**: the GitHub token goes only to api.github.com. Raw files are public and fetched without it, and path parts
  are checked (no `..`, no `?`) before they go into a URL.

### One alternative I rejected
**Fetching the published HTML from docs.spring.io** and stripping tags. The AsciiDoc source at a git tag is exact, versioned
and has the section anchors right in it; scraping HTML depends on the site's layout.

### Likely interview questions
1. **How do you stop the LLM from making things up in the draft?** Only retrieved sources above a similarity threshold go in;
   the prompt says use only them and cite them; no sources means no draft; links are checked against the sources afterwards.
   And a maintainer reviews it: it's never auto-posted.
2. **How did you choose the chunk size?** From the embedding model: MiniLM truncates at 256 word pieces, so ~1,200 characters
   with 200 overlap, and the heading first so it's always inside the window.
3. **How would you know if retrieval is good?** The STOP A hand-scoring of 30 real issues (useful / partly / wrong). Next: a
   small labelled set of issue → right docs section to measure recall@5 of the docs search itself.

## M4 step 5: the triage report, created by the Kafka worker (4 Nov 2026)

Files: Flyway `V8__triage_report.sql`; package `report`: `TriageService`, `TriageReport`, `TriageReportRepository`,

### What it does
For one issue, `TriageService` runs every part and stores the result as one row:

2. **duplicate_check**: the LLM "same root problem?" check, only if the top match scores ≥ 0.825 (sai's comment threshold);
3. **labels** (vote), 4. **missing** details (LLM), 5. **fixed_hint** (only if the top match scores ≥ 0.75), 6. **draft_reply** (RAG);

- **jsonb parts read back as `JsonNode`**: the API returns the stored JSON as it is. If a Java record changes later, old

- **`ResponseEntity.of(Optional)`**: 200 with the body if present, 404 if empty, in one line.

**One normalized table per part** (report_label, report_duplicate, ...). Many joins for data that is always read and
written together, never queried inside. jsonb is simpler here, and the plan's schema asked for it.

### Likely interview questions
1. **What happens if the LLM is down when an issue is opened?** The LLM parts say UNKNOWN with the reason; duplicates,

   Kafka's retry + DLT handle that.
2. **How do you avoid paying twice for a redelivered event?** Check for an existing report before any LLM call; UNIQUE
   (issue_id) as a backstop.
3. **Why run the LLM duplicate check only above a threshold?** Cost and purpose: it exists to decide a public comment, which
   needs a high score anyway. Below it, the maintainer still sees the private top 3.

## M4 step 7: cost guard, a daily token budget (4 Nov 2026)

Files: Flyway `V9__llm_usage.sql`, `ai/TokenBudget.java`, `ai/GuardedTriageLlm.java`, `LlmConfig` (wraps the LLM),
`TriageService` (notes); config `triage.llm.daily-token-budget: 200000`; tests `GuardedTriageLlmTest` (2),
`TokenBudgetDbTest` (1), one new case in `TriageServiceDbTest`.

### What it does
Every LLM call goes through `GuardedTriageLlm`. Before the call it asks `TokenBudget` whether today (UTC) is still under
the budget; after the call it adds the call's tokens to today's row in `llm_usage`. Over the budget, the call is refused

### Basics used here

### Likely interview questions
1. **How do you control LLM cost?** Prompts only where needed (the duplicate check only above the threshold, no draft without

2. **Can the budget be exceeded?** By at most the in-flight calls: the check is before the call and the count after. Fine for

3. **What does a maintainer see when the budget is hit?** The report still has duplicates, labels and the fixed hint; the LLM

## M5 step 0: transactional outbox (4 Nov 2026)

Files: Flyway `V10__outbox_event.sql`; package `outbox`: `OutboxRepository`, `OutboxEvent`, `OutboxRelay`, `SchedulingConfig`;
`WebhookIntakeService` (writes the outbox row), `IssueEventPublisher.sendAndWait`, `GitHubWebhookController` (500 on a DB
error); tests `OutboxRelayTest` (4), `OutboxRepositoryDbTest` (2), `WebhookDeliveryDbTest` (2 new), `WebhookIntakeServiceTest`
(rewritten), `OutboxKafkaDownEndToEndTest` (1, real Postgres + real Kafka).

### What it does
- **Webhook path**: in ONE database transaction, insert the `webhook_delivery` row (a repeat → "duplicate", stop) and an
  `outbox_event` row with the Kafka topic, key and JSON message. Then answer GitHub. **Kafka isn't called here any more.**
- **Relay**: every 500 ms (Spring `@Scheduled`), take up to 100 unsent rows oldest first (`FOR UPDATE SKIP LOCKED`), send
  each to Kafka and wait for the ack, then set `sent_at`. On a failure: `attempts + 1`, `last_error`, and **stop the batch**,
  so a later event of the same issue never overtakes an earlier one. Sent rows are deleted after 7 days.
- **Crash between "Kafka has it" and "marked sent"**: the row is sent again on the next run, so it's "at least once". The consumer
  is already idempotent (upsert ignores older data, one report per issue), so a repeat is harmless.

### Why (the problem it fixes)
M2 published to Kafka *inside* the DB transaction. Two bad cases: Kafka down → the webhook failed with 500 (GitHub only
redelivers by hand); Kafka acked but the commit failed → the event was out but not recorded. You can't make "write to
Postgres" and "write to Kafka" one atomic step. The outbox turns it into one Postgres transaction plus a retryable copy job.

### Basics used here
- **Transactional outbox pattern**: before: `save(); kafka.send();` (two systems, no shared transaction). After: `save();
  outbox.add();` in one transaction, and a relay copies outbox → Kafka until it succeeds.
- **`@Scheduled(fixedDelayString = "${triage.outbox.poll-ms:500}")`**: Spring calls the method again 500 ms after the
  previous call *ended* (fixedDelay: runs never overlap). It needs `@EnableScheduling` once (`SchedulingConfig`), which can be
  switched off with `triage.outbox.relay-enabled=false` (the Kafka-down test uses that to control the relay by hand).
- **`SELECT ... FOR UPDATE SKIP LOCKED`**: lock the rows I'm taking; rows another transaction has locked are skipped, not
  waited for. Two app instances can run the relay without sending a row twice at the same time.
- **Partial index** (`WHERE sent_at IS NULL`): indexes only the unsent rows, which is all the relay ever asks for.

### One alternative I rejected
**Debezium / change data capture** (Kafka Connect reads Postgres's write-ahead log and publishes the outbox rows). It's the
production-grade version, but it needs a Kafka Connect cluster and logical replication: too much to run on a 2-CPU VM for
one table. The polling relay is ~60 lines and easy to explain.

### Likely interview questions
1. **What is the transactional outbox and why did you need it?** You can't commit to Postgres and Kafka atomically. So the
   webhook writes the event to an outbox table in the same transaction as its own data, and a relay publishes it later.
   No lost events, and webhooks are accepted even when Kafka is down.
2. **Can a message be sent twice?** Yes, if the app dies after Kafka's ack but before `sent_at` is written. That's at-least-once,
   so the consumer must be idempotent: ours upserts by GitHub id, ignores older updates, and creates a report only once.
3. **How do you keep per-issue order?** The relay sends in id order and stops at the first failure, and the Kafka key is the
   issue, so one issue's events go to one partition in order.

## M5 step 2: k3s manifests (4 Nov 2026)

Files: `deploy/k3s/00-namespace.yaml`, `10-postgres.yaml`, `20-kafka.yaml`, `30-app.yaml`, `secret.example.yaml` (template only;
`secret.yaml` and `*.pem` are git-ignored); test `K3sManifestsTest` (3). kubectl isn't installed on the build Mac, so there was
no `kubectl apply --dry-run`; the test parses the files and checks them instead.

### What it does
- **Postgres** (pgvector image) and **Kafka** (KRaft, one broker) as **StatefulSets** with persistent volumes (k3s's local-path
  storage: a folder on the VM's disk), each behind a Service (`postgres:5432`, `kafka:9092`). Kafka advertises its in-cluster
  DNS name, so the app can reach it.
- **The app** as a Deployment: env from the `triage-secrets` Secret, the GitHub App key mounted as a file (optional: without it,
  shadow mode only), eval output to /tmp, and three probes: **startup** (up to 5 min, because loading the model + Flyway takes
  ~45 s on a small VM), **liveness**, **readiness** (Spring Boot's `/actuator/health/liveness|readiness`).
- An **Ingress** for k3s's built-in Traefik (host is a placeholder until STOP B).
- **Sizing for 2 OCPU / 12 GB** (Oracle Always Free since mid-2026, per several reports; Oracle's own page still showed 4 / 24
  when checked, so sai should confirm in the console): requests 1.1 CPU / 3.5 GB, memory limits 6 GB in total, leaving room for
  k3s itself.

### Basics used here
- **Deployment vs StatefulSet**: a Deployment's pods are interchangeable (the app). A StatefulSet gives each pod a stable name and
  **its own** volume that survives restarts (databases, Kafka).
- **requests vs limits**: requests = what the scheduler reserves; a memory limit = the pod is killed if it uses more. No CPU
  limit on purpose (CPU over the request is just slowed, never killed).
- **Probes**: startup ("has it finished starting?"), liveness ("is it stuck? restart it"), readiness ("can it take traffic?").
  Without a startup probe, a slow start would be killed by the liveness probe in a loop.
- **Secrets**: the repo has only a template with placeholders; the real values are typed on the server. A test fails if
  `secret.yaml` ever appears in the repo.

**Helm charts.** Templating and releases for four objects on one VM is more to learn and explain than plain YAML applied in order.

### Likely interview questions
1. **Why StatefulSets for Postgres and Kafka?** Stable identity and a volume per pod that survives restarts; a Deployment would

2. **How did you size it for a 2-CPU / 12-GB VM?** Requests add up to 1.1 CPU / 3.5 GB and memory limits to 6 GB, leaving room for

3. **How do secrets get to the pod?** A Kubernetes Secret created on the server from a template (never committed), injected as

## M5 step 3: GitHub App authentication without a new library (4 Nov 2026)

Files: `github/GitHubAppAuth.java`, `github/PemKeys.java`, config `github.app.id` / `github.app.private-key-path` (from the
`GITHUB_APP_ID` / `GITHUB_APP_PRIVATE_KEY_PATH` env vars); tests `GitHubAppAuthTest` (3), `PemKeysTest` (4). The tests make
their own throwaway RSA key; no real key exists anywhere in the repo.

### What it does
1. **App JWT**: `{"alg":"RS256"}` . `{"iat": now - 60 s, "exp": now + 9 min, "iss": "<app id>"}`, each base64url, signed with
   the App's private key using `java.security.Signature("SHA256withRSA")`. It proves "I am this App".
2. **Installation token**: with the JWT, `GET /repos/{owner}/{repo}/installation` → installation id (cached), then
   `POST /app/installations/{id}/access_tokens` → a 1-hour token that can act on that repo with the App's permissions.
3. **Cache**: the token is reused until 5 minutes before `expires_at`. Tested with a clock the test moves: 54 min = cached,
   56 min = refreshed.
4. **Key format**: GitHub downloads keys as PKCS#1 (`BEGIN RSA PRIVATE KEY`), Java reads only PKCS#8. `PemKeys` adds the small
   PKCS#8 header (version + "rsaEncryption" + the key as an OCTET STRING) by hand. The test checks the result is byte-for-byte
   what Java itself produces.

### Basics used here
- **JWT**: three base64url parts, `header.payload.signature`. The server checks the signature with the App's public key and the
  `exp` time; nobody can change the payload without the private key.
- **RS256**: an RSA signature over the SHA-256 hash of `header.payload`.
- **DER/ASN.1**: the binary format keys are stored in. Each value is tag + length + bytes; lengths ≥ 128 use a "long form"
  (0x82 0x04 0xA6 = 1,190).
- **`synchronized`**: two threads asking for a token at the same time won't both fetch one (the cache is a plain HashMap).

### One alternative I rejected
**A JWT library (jjwt / nimbus) or BouncyCastle for PEM.** Both are new dependencies for ~60 lines of standard-library code that
the plan asked for, and the hand-written version is easier to explain line by line.

### Likely interview questions
1. **How does a GitHub App authenticate?** Sign a short-lived JWT with the App's private key, exchange it for an installation
   token per installation, and use that (1 hour) for API calls; cache it and refresh shortly before expiry.
2. **Where is the private key?** In a file on the server, mounted from a Kubernetes Secret; its path comes from an env var.
   It's never in git, never logged, and tests use generated keys.
3. **Why iat 60 s in the past?** Clock drift: if our clock is ahead of GitHub's, a token "issued in the future" is rejected.

## M5 step 4: comment mode, off by default and never twice (4 Nov 2026)

Files: Flyway `V11__comment_mode.sql` (`repo_setting`, `posted_comment`); package `comment`: `CommentService`,
`CommentRepository`, `GitHubCommentClient`, `CommentProperties`; `TriageService.createIfMissing` calls it; config
`triage.comments.skip-labels`; tests `CommentServiceDbTest` (4), `CommentServiceTest` (1), `GitHubCommentClientTest` (1).

### What it does
After the worker creates a new issue's report, `CommentService` may post **one** comment as the GitHub App, only if all of
these are true (checked in this order):
1. the repo's mode is `SUGGEST` (no row in `repo_setting` = `SHADOW` = never);
2. the App is configured (id + key file);
3. the issue is open and was opened by someone **outside the team**;
4. it has none of the repo's **skip labels** (spring-boot: `status: forward-port`, `status: back-port`, the clones that were
   21 of 48 confirmed false alarms in step 1);
5. the top match scores ≥ **0.90** AND the LLM check said **yes**;
6. a `posted_comment` row can be **reserved** for the issue (INSERT ... ON CONFLICT DO NOTHING): only then post, then mark
   POSTED (or FAILED, not retried).

The comment: "This looks like it may be a duplicate of #N (title), similarity 93%. A bot suggested this after an automated
check; it can be wrong. The maintainers decide."

### Why these choices
- **Reserve before posting = at most once.** If the app crashes after posting but before recording, the row is PENDING and
  nothing posts again. The opposite order (post, then record) could post twice on a Kafka redelivery. A missing comment is
  cheap; a double bot comment on someone's issue is embarrassing.
- **No HTTP endpoint to switch it on.** Turning on public comments is a deliberate operator act (`INSERT INTO repo_setting
  VALUES ('owner/name', 'SUGGEST')`), so nobody on the internet can flip it.
- **Only for reports from the worker**: regenerating a report by hand (`POST /reports`) never comments.

### Basics used here
- **At-most-once vs at-least-once**: Kafka and the outbox are at-least-once (repeat rather than lose); for a public side effect
  we want at-most-once (lose rather than repeat). A unique key reserved before the side effect gives that.
- **Feature flag in data**: a row per repo, defaulting to off, read on each decision; no redeploy to change it.
- **Guard clauses**: each check returns a named `Decision` (SHADOW_MODE, TEAM_AUTHOR, SKIP_LABEL...), so logs and tests say exactly
  why nothing was posted.

### One alternative I rejected
**Posting from the report endpoint or the demo page.** Comment decisions belong to the event pipeline, once per new issue;
a button would make double posts and accidental posts easy.

### Likely interview questions
1. **How do you make sure the bot never comments twice?** A row keyed by issue id is inserted before posting with ON CONFLICT DO
   NOTHING; only the caller that inserted it may post. Redeliveries, retries and a second instance all find the row and stop.
2. **When does it comment at all?** Only in repos switched to SUGGEST by the operator, only on open issues from outside the team
   that aren't bookkeeping clones, and only when the match is ≥ 0.90 and the LLM agrees. Everything else stays in the private report.
3. **What if posting fails?** The row becomes FAILED with the error, and it's not retried. The private report still has the match.

## M5 fix: admin endpoints must not be public (4 Nov 2026)

Found in review before deploying: the Ingress routed `/` to the app, so on the public VM **anyone** could call
`POST /backfill/{any}/{repo}` (uses up the GitHub token's quota, fills the disk), `POST /embeddings`, `POST /docs`, `POST /eval`
(minutes of CPU, LLM calls) and `POST /reports/...` (LLM spend).

Files: `web/AdminTokenFilter.java`, config `triage.admin-token` (`TRIAGE_ADMIN_TOKEN`), `static/index.html` (optional "Admin" box),
`deploy/k3s/30-app.yaml` (env + an Ingress with only the public paths), `secret.example.yaml`, the scoring scripts (send the
header from the env var), README and `docs/m5-report.md`; tests `AdminTokenFilterTest` (4), one in `WebhookEndToEndTest` (the real
app refuses all five admin POSTs without the token), one in `K3sManifestsTest`, more checks in `DemoPageTest`.

### What it does
- **Two locks.** (1) The app: every request that isn't GET/HEAD/OPTIONS, except `POST /webhooks/github` (which has its own HMAC
  check), needs header `X-Admin-Token` equal to `TRIAGE_ADMIN_TOKEN`. Not configured → **503** ("fail closed", like the webhook
  secret); missing/wrong → **401**. (2) The Ingress routes only what the public needs: the webhook, the page, `/reports`, `/repos`,
  `/settings`, `/actuator/health`. Admin paths aren't reachable from outside at all; operators use `kubectl port-forward`.
- **Constant-time compare** (`MessageDigest.isEqual`): a normal `equals` stops at the first wrong character, so response times
  could leak how much of a guess was right.
- **Demo page**: "Create report" only appears after pasting the token into the Admin box; it's sent as a header, kept in
  `sessionStorage` (this tab only), never in the URL. Without it: "Only existing reports can be viewed on the public demo."
- Checked in the browser on a local run: no token → that message; right token → report created; wrong token → "not accepted".

### Basics used here
- **Defense in depth**: the Ingress can't filter by HTTP method (POST /reports shares a path with GET /reports), so the app
  check is the real lock and the Ingress narrows what's exposed.
- **`OncePerRequestFilter`**: a Spring servlet filter that runs once per request before any controller. `shouldNotFilter` skips
  reads and the webhook, so the rule is in one place instead of in every controller.
- **Fail closed**: if the secret is missing, refuse, rather than silently allowing everything.

### One alternative I rejected
**Spring Security** with users and roles. Correct for a product with logins, but a new dependency and a lot of configuration for
one shared operator secret on five endpoints.

### Likely interview questions
1. **How did you secure the admin endpoints?** A filter requiring a shared token header, compared in constant time, failing
   closed when not configured; plus an Ingress that doesn't expose admin paths, and port-forwarding for operators.
2. **Why not just hide the URLs?** Obscurity isn't protection; anyone can guess `/backfill/...` from the open-source code.
3. **Why is the webhook exempt?** GitHub can't send our admin token; it signs the body with HMAC-SHA256, which the receiver already
   verifies.

## M6 step 1: Prometheus metrics with Micrometer (4 Nov 2026)

Files: `pom.xml` (`micrometer-registry-prometheus`, approved in the plan, version from Spring Boot), `metrics/TriageMetrics.java`,
hooks in `GuardedTriageLlm` (tokens + cost), `KafkaErrorHandlingConfig` (dead letters), `IssueEventConsumer` (webhook→report
time), `TriageService` (duplicate level), `CommentService` (decision), `OutboxRelay` (unsent gauge); `application.yml` exposes
`/actuator/prometheus` (on the app port only: it's not in the public Ingress paths). Tests: `TriageMetricsTest` (3), plus checks
in `GuardedTriageLlmTest`, `IssueEventConsumerTest`, `CommentServiceDbTest` and `WebhookEndToEndTest` (the real endpoint).

### The metrics
| Prometheus name | Type | What |
|---|---|---|
| `triage_webhook_to_report_seconds` | histogram | accepted webhook (`webhook_delivery.received_at`) → stored report |
| `triage_llm_tokens_total{model,direction}` | counter | input / output tokens |
| `triage_llm_cost_usd_total{model}` | counter | tokens × list price (Haiku 5.5: $0.10 / $0.50 per million) |
| `triage_kafka_dead_letters_total{exception}` | counter | messages sent to issue-events.DLT, by real cause |
| `triage_duplicates_suggested_total{level}` | counter | each new report's top match: high / medium / low / none |
| `triage_comments_total{decision}` | counter | comment mode: SHADOW_MODE, BELOW_THRESHOLD, POSTED... |
| `triage_outbox_unsent` | gauge | outbox rows not yet sent (grows while Kafka is down) |
| `kafka_consumer_fetch_manager_records_lag_max` | gauge | consumer lag, from Spring Boot's Kafka client metrics |

"Tokens per day" is a query, not a metric: `increase(triage_llm_tokens_total[1d])`.

### Basics used here
- **Micrometer** is to metrics what SLF4J is to logging: you record to a neutral API (`Counter`, `Timer`, `Gauge`), and a
  registry (here Prometheus) decides the format. Before: `log.info("took {} ms")` and grep. After: a time series you can graph and alert on.
- **Counter vs gauge vs timer**: a counter only goes up (tokens used); a gauge is "the value right now" (unsent rows); a timer
  records durations. With `publishPercentileHistogram()` it exports buckets, so Prometheus can compute p50/p95 over any window
  with `histogram_quantile`.
- **Tags (labels)**: one metric, split by model or decision. Keep their values few (never an issue number), or Prometheus stores
  one series per value.
- **Pull model**: Prometheus scrapes `/actuator/prometheus` every N seconds; the app just keeps the numbers.

### One alternative I rejected
**Computing p95 in the app** (Micrometer's client-side percentiles). They can't be combined across instances or time windows;
histogram buckets can, in Prometheus.

### Likely interview questions
1. **What do you monitor?** The user-facing latency (webhook to report, p50/p95), LLM tokens and cost, Kafka lag and dead letters,
   the outbox backlog, and what the assistant decided (duplicate levels, comment decisions).
2. **How do you get p95 latency?** A Micrometer timer with a percentile histogram; Prometheus computes
   `histogram_quantile(0.95, sum(rate(triage_webhook_to_report_seconds_bucket[5m])) by (le))`.
3. **Why not put the issue number in a tag?** High cardinality: every value is a new time series, which blows up Prometheus'
   memory. Per-issue detail belongs in logs and the database.

## M6 step 3: load test (4 Nov 2026)

Files: `scripts/load-test.py` (standard library only), `KafkaErrorHandlingConfig` (now logs every dead letter), README "Load test";
test: one more in `KafkaTopicsConfigTest` (the dead-letter log shows the real cause).

### What it does
Sends N signed `issues opened` webhooks (HMAC-SHA256, exactly like GitHub) for synthetic issues numbered 900000+ in spring-boot,
with P parallel senders; records each HTTP response time; then reads `triage_report.created_at` per issue from Postgres to get
the end-to-end time; prints p50/p95; and deletes everything it created (issues cascade to embeddings and reports; deliveries;
outbox rows). The app runs with the fake LLM, so it costs nothing.

**Result (500 webhooks, 10 senders):** receiver p50 7 ms / p95 13 ms; all 500 reports; end to end p50 23.1 s / p95 43.3 s, because
500 arrived in 0.4 s and one worker thread makes ~10.4 reports/s (a single report alone: 0.23 s).

### What the test found
The first smoke run's synthetic issues lacked `repository_url`, so the mapper failed and all 5 went to the dead-letter topic,
**with nothing in the log**. Only the new `triage_kafka_dead_letters_total` metric showed it. Now every dead letter writes an error
line with the key, partition, offset and the real cause. The script also gives up after 60 s without progress instead of waiting 15
minutes.

### Basics used here
- **Receiver latency vs end-to-end latency**: the receiver only writes two rows and answers (7 ms); the work happens later from
  Kafka. With a burst, end-to-end time is mostly **queueing**: Little's law, wait ≈ backlog / throughput (500 / 10.4 ≈ 48 s for the
  last one).
- **Percentiles**: p50 = the typical case; p95 = the slowest 1 in 20. Averages hide the tail.
- **Test data hygiene**: unique, recognisable ids (900000+, `loadtest-*` delivery ids) so cleanup can't touch real rows.

### One alternative I rejected
**A load-testing tool (k6, Gatling, JMeter).** Better for big tests, but a new tool to install; 70 lines of Python with threads
send 1,200 webhooks/s here, which is plenty for one VM.

### Likely interview questions
1. **How fast is it?** The webhook receiver answers in 7 ms (p50), 13 ms (p95) under a burst of 500, well within GitHub's 10 s;
   a single report takes ~0.2 s plus the LLM calls; a burst queues in Kafka and drains at ~10 reports/s per worker thread.
2. **How would you scale it?** More listener threads (one per partition, 3 today), more partitions and app instances; the
   database and the LLM (rate limits, cost) become the next limits.
3. **What did the load test teach you?** That dead letters were silent: only the metric caught them. Now they're logged with the
   cause, and the dashboard turns red at the first one.

## Backend piece 1: installing the GitHub App adds the repository (8 Nov 2026)

**What it does.** When someone installs the GitHub App on a repository, GitHub sends an `installation` webhook (action
`created`, with a `repositories` list). Repositories added to an existing installation later arrive as
`installation_repositories` (action `added`, list `repositories_added`). For each **public** repository the webhook puts one row in a new
table, `repo_job` (Flyway V12), with status `QUEUED`, and answers GitHub at once. A background runner (`RepoJobRunner`) picks the oldest queued
job every 5 seconds and does three steps in order:
1. **BACKFILL**: load every past issue (the same `BackfillService` the admin endpoint uses), writing "issues so far" after each page.
2. **EMBEDDINGS**: embed the issues that have no vector yet, writing "done of total" after each batch of 256.
3. **DOCS**: load the reference docs if application.yml lists them for this repo. If it doesn't, the job still finishes (`DONE`) with a
   note: "no reference docs, so its reports have no draft reply".
Anyone can read the progress at `GET /repos/{owner}/{repo}/job`. The operator can start a job by hand with
`POST /repo-jobs/{owner}/{repo}` (admin token).

**Why this way.**
- **A queue table, not work inside the webhook.** GitHub waits only 10 seconds for an answer, and loading spring-boot took about 18 minutes.
  The webhook only inserts rows, which takes milliseconds.
- **One transaction for the delivery id and the jobs.** A redelivered webhook finds its delivery id and queues nothing. A partial unique index
  (`ON repo_job (lower(repo)) WHERE status IN ('QUEUED','RUNNING')`) also stops two open jobs for the same repository, even if they come
  from two different deliveries or the operator.
- **Progress commits as it goes.** The runner has no transaction around the job. Each progress `UPDATE` commits on its own, so the
  status endpoint shows the job moving. One big transaction would hide everything until the end, and hold locks for 20 minutes.
- **Claiming with `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *`.** One statement takes the job and marks it
  `RUNNING`. A second app instance asking at the same moment skips the locked row instead of taking the same job.
- **Restart recovery.** On startup (`@PostConstruct`, before the scheduler starts), `RUNNING` jobs go back to `QUEUED`. This is safe
  because every step can run again: the backfill upserts, embeddings only fill gaps, and docs replace the old ones. It assumes one app
  instance (the k3s Deployment has 1 replica).
- **Three scheduler threads.** Spring's `@Scheduled` uses a single thread by default. A 20-minute job on that thread would stop the outbox
  relay (every 500 ms) from sending webhooks to Kafka. There are three scheduled tasks (job runner, relay, hourly outbox clean-up), so
  `spring.task.scheduling.pool.size: 3` gives each one its own thread. Switching scheduling off (`triage.outbox.relay-enabled=false`)
  also stops repo jobs.
- **Public errors are short.** The status endpoint is public, so a failed job shows only a plain reason ("GitHub answered 404",
  "Database error"). The full exception, which can contain SQL or a response body, goes to the log only.
- **Private repositories are skipped.** The reports site is public, so loading a private repository would publish its issues. A
  repository whose `private` flag is missing is treated as private.

**Rejected alternative.** Sending the job through Kafka like issue events. That would give retries and a dead-letter topic for free, but
a 20-minute message would exceed the consumer's `max.poll.interval.ms` (5 minutes), so Kafka would think the worker died and hand the
job to another one. Progress would also still need a table. A database table is the simpler fit for few, long jobs.

### Likely interview questions
1. *Why not do the backfill inside the webhook request?* GitHub times out after 10 seconds and would redeliver. The webhook only
   records the work (a row in `repo_job`) and a background runner does it, which is the same idea as the outbox.
2. *What happens if the app crashes in the middle of a job?* The row stays `RUNNING`. At the next startup it goes back to `QUEUED`
   and runs again from the first step. Every step is idempotent, so running it twice gives the same data.
3. *How do you stop the same repository being loaded twice at the same time?* A partial unique index allows only one `QUEUED` or
   `RUNNING` row per repository (case-insensitive). The insert uses `ON CONFLICT ... DO NOTHING`, so a second request is a no-op,
   and `SKIP LOCKED` means two runners never claim the same job.

## Backend piece 2: nightly database backup (8 Nov 2026)

**What it does.** `deploy/k3s/40-backup.yaml` adds a Kubernetes **CronJob**: every night at 02:30 India time it starts a short-lived pod
that runs `pg_dump` against the `postgres` Service. It writes `triage-<date>.dump` to its own volume (`postgres-backups`, 10 GB) and
deletes dumps older than 7 days. Restore uses `pg_restore` (steps in docs/m5-report.md).

**The parts, from the basics.**
- **CronJob**: Kubernetes' version of cron. On the `schedule` it creates a **Job**, and the Job runs a Pod until it exits 0.
  `timeZone: Asia/Kolkata` makes "30 2 * * *" mean 02:30 in India (without it, the schedule follows the kube-controller-manager's time zone; on k3s that runs inside the k3s server, so it's the VM's zone, UTC).
- **concurrencyPolicy: Forbid**: if last night's dump is somehow still running, tonight's run is skipped instead of starting a second one.
- **backoffLimit: 2, restartPolicy: Never**: a failed dump is tried twice more in fresh pods, then the Job shows as Failed
  (`kubectl get jobs`).
- **startingDeadlineSeconds: 3600**: if the VM was off at 02:30 and comes back within the hour, the backup still runs.
- **pg_dump --format=custom**: Postgres's own compressed archive (113 MB for today's 43,810 issues plus embeddings). Unlike a plain
  `.sql` file, `pg_restore` can restore one table out of it or list what's inside (`pg_restore --list`).
- **Same image as Postgres** (`pgvector/pgvector:pg16-trixie`): `pg_dump` must be at least the server's version, and the same image is
  the simplest way to guarantee it. A test checks that the two images stay equal.
- **Write to `.part`, then `mv`**: a dump that fails half-way never sits there looking like a good backup. `mv` within one filesystem is
  an atomic rename.
- **Password**: from the same `triage-secrets` Secret as Postgres (`PGPASSWORD`, which pg_dump reads by itself). Never in the file.

**Tested locally** by running the same script in the same image against the docker-compose Postgres. It wrote a 113 MB dump,
`pg_restore --list` read it, and the 7-day cleanup deleted an old `.dump` and an old `.part` while keeping a new one.

**Rejected alternative.** Streaming the WAL (write-ahead log) with a tool like pgBackRest or WAL-G for point-in-time recovery. That is
the production answer (lose seconds, not a day), but it needs extra software and object storage. For a demo database that can be
rebuilt from GitHub in about 20 minutes, a nightly dump is enough.

**Limit, said plainly.** The dumps live on the same VM disk. They protect against a bad migration, a wrong DELETE or a broken
Postgres volume, not against losing the VM. Copy one off the VM now and then (m5-report has the steps).

### Likely interview questions
1. *How would you restore last night's backup?* Scale the app to 0, run `pg_restore --clean --if-exists` from the dump into
   postgres-0, then scale the app back to 1. Flyway sees the restored `flyway_schema_history` and runs any newer migrations. One catch: `--clean` only
   drops what is in the dump, so if a migration ran after the dump, restore into a fresh database (or drop those newer tables first).
2. *Why a CronJob and not a cron line on the VM?* It is declared next to the database in the same manifests, uses the same Secret,
   gets retries and a history of runs, and keeps working if the cluster moves to another machine.
3. *What's your RPO (recovery point objective)?* Up to 24 hours of data with a nightly dump. Lower would need WAL archiving. Issues can
   also be re-fetched from GitHub, so the real loss is reports and LLM spend.
