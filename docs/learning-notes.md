# Learning notes

One section per piece: what it does, why this way, one rejected alternative, and likely

## M1 piece 1: Issue entity + SourceType enum + IssueRepository (3 Nov 2026)

Files:
- `src/main/java/com/saisanketh/triage/domain/SourceType.java`
- `src/main/java/com/saisanketh/triage/domain/Issue.java`
- `src/main/java/com/saisanketh/triage/repository/IssueRepository.java`

### What it does
- `SourceType` is an enum with one value, `GITHUB`. It says which tracker an issue came from.
- `Issue` is a JPA entity: one Java object = one row in the `issue` table from `docs/schema.md`.
  Each field has a `@Column` that sets the column name, length and whether it can be null.
  The labels are a `Set<String>` stored in a second table, `issue_label`.
- `IssueRepository` is an interface. Spring Data writes the code for it at startup, so we get
  `save`, `findById`, `findAll` and so on for free. We add one method,
  `findBySourceAndExternalId`, which piece 5 (upsert) uses to ask "have we stored this issue already?"

### Why this way
- **The table is created from the entity** (`ddl-auto: update`), so the annotations carry the
  whole schema: the unique constraint `(source, external_id)` and the index `(repo, created_at)`
  are declared in `@Table`, and the label index in `@CollectionTable`. Checked in Postgres
  with `\d issue`: it matches `docs/schema.md`.
- **`@Enumerated(EnumType.STRING)`** stores `'GITHUB'`, not `0`. With the default (ORDINAL),
  adding or reordering enum values would silently change what old rows mean.
- **`Instant` for times**: an `Instant` is one exact moment in UTC, and Hibernate maps it to
  `timestamptz`. GitHub sends UTC times, so nothing is lost or shifted.
- **`raw` as `String` + `@JdbcTypeCode(SqlTypes.JSON)`**: Postgres stores it as `jsonb` (it checks that
  it is valid JSON and can index into it later), but in Java it's a plain string. We never
  read fields from it in Java, so a string is enough.
- **`columnDefinition = "text"`** for title, body and URL: a plain `String` would become
  `varchar(255)`, and long issue bodies would fail to insert.
- **Labels as `@ElementCollection`**: a label here is just a name with no id of its own, so
  it doesn't need its own entity. `Set` (not `List`) means the same label can't appear twice,
  which matches the primary key `(issue_id, label_name)`. `@OnDelete(CASCADE)` puts
  `ON DELETE CASCADE` on the foreign key, as in the schema.
- **Lombok `@Getter @Setter @NoArgsConstructor`, not `@Data`**: `@Data` also generates
  `equals`, `hashCode` and `toString` from all fields. On an entity that is a trap: the id
  changes from null to a value on save (so `hashCode` changes and the object gets "lost" in
  a `HashSet`), and `toString` would touch the lazy `labels` collection and print the
  whole `raw` JSON. JPA needs the no-args constructor; setters are used by the mapper in piece 4.

### One alternative I rejected
**Writing the schema as SQL with Flyway** (`V1__create_issue.sql`) and setting
`ddl-auto: validate`. That is what I'd use in production: every schema change is a
versioned, reviewed file. I didn't do it now because it adds a dependency (the rules say ask first)
and `ddl-auto: update` is fine for a single developer while the schema is still changing.
Worth switching before M3, see the gotcha below.

### Two things Hibernate did differently from docs/schema.md
1. `id` is `bigint generated by default as identity`, not `bigserial`. These work the same way.
   Identity columns are the SQL-standard form and are preferred in modern Postgres.
2. Hibernate added `CHECK (source = 'GITHUB')` because the column is an enum. **Gotcha:** when
   we add `JIRA`, `ddl-auto: update` will *not* update this check, so inserts of Jira issues
   will fail until the constraint is changed by hand (or by a Flyway migration).

### Likely interview questions
1. **Why is the unique key `(source, external_id)` and not just `external_id`?**
   Ids are only unique within one tracker. A GitHub id and a Jira id could collide.
   Together they identify an issue anywhere, and they're what makes the backfill safe to re-run:
   find by that key, update if found, insert if not.
2. **Why `EnumType.STRING` instead of the default?**
   ORDINAL stores the position (0, 1, …). If someone adds a value in the middle of the enum,
   every existing row now points at the wrong value, and no error is raised. STRING stores the
   name, so it's readable in SQL and safe to extend.
3. **Why not use `@Data` on a JPA entity?**
   Its generated `equals`/`hashCode` use every field, including the generated id, which is
   null before save and set after, so the hash changes. Its `toString` can trigger lazy loading
   (or a `LazyInitializationException`) and dump huge fields. Use `@Getter`/`@Setter` and only
   write `equals`/`hashCode` if you need them (based on the id or the natural key).

## M1 piece 2: IssueSource + GitHubIssueSource, one page (3 Nov 2026)

Files:
- `src/main/java/com/saisanketh/triage/github/IssueSource.java`
- `src/main/java/com/saisanketh/triage/github/IssuePage.java`
- `src/main/java/com/saisanketh/triage/github/GitHubIssueSource.java`
- `src/test/java/com/saisanketh/triage/github/GitHubIssueSourceTest.java`
- `src/main/resources/application.yml` (new `github:` block)

### What it does
- `IssueSource` is an interface with one method: `fetchPage(owner, repo)`. The rest of the app
  will depend on this interface, not on GitHub directly.
- `IssuePage` is a Java `record` (a small immutable data class) holding two things: the list of
  issues as raw JSON (`JsonNode`), and the raw `Link` header (which tells us the URL of the next
  page; piece 3 reads it).
- `GitHubIssueSource` implements the interface. It sends
  `GET https://api.github.com/repos/{owner}/{repo}/issues?state=all&per_page=100` with three headers:
  `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28` (pins the API
  version so GitHub can't change the response under us) and `Authorization: Bearer <token>`.
- The token comes from the environment: `application.yml` has `token: ${GITHUB_TOKEN:}`, which
  means "use the env var GITHUB_TOKEN, or empty if it isn't set". The code never contains a token.

### Why this way
- **RestClient**: Spring's modern synchronous HTTP client (Spring 6.1+). It reads like a sentence
  (`get().uri(...).retrieve().toEntity(...)`) and throws an exception on 4xx/5xx by default.
- **`toEntity(...)`, not `body(...)`**: `body` gives only the JSON; `toEntity` also gives the
  response headers, and we need the `Link` header.
- **URI template `{owner}/{repo}`**: RestClient fills in and URL-encodes the values, so a strange
  repo name can't break the URL.
- **`JsonNode`, not a Java class per field**: we store the full JSON in the `raw` column anyway,
  and piece 4 picks out the fields it needs. Note: Spring Boot 4 uses **Jackson 3**, so the
  import is `tools.jackson.databind.JsonNode` (Jackson 2 was `com.fasterxml.jackson...`).
- **No token = warning, not a crash**: public repos work without a token, but only for 60
  requests/hour (5,000 with a token). Crashing at startup would also stop work that
  doesn't touch GitHub.
- **Two constructors**: Spring uses the public `@Autowired` one, which reads the config. The test
  uses the package-private one and passes in a `RestClient.Builder` bound to a fake server.
  Spring Boot 4 only auto-configures a `RestClient.Builder` bean if the `spring-boot-restclient`
  module is on the classpath, and it isn't (adding it would be a new dependency), so we
  call `RestClient.builder()` ourselves.
- **Test with `MockRestServiceServer`**: it replaces the HTTP layer inside RestClient, so the test
  checks the real URL, headers and JSON parsing, but never touches the network. 4 tests:
  correct request + items + Link header; last page has no Link header; no token = no
  `Authorization` header; 404 throws `HttpClientErrorException.NotFound`.

### One alternative I rejected
**Mocking `RestClient` itself with Mockito.** RestClient is a fluent chain
(`get()` -> `uri()` -> `retrieve()` -> ...), so you'd have to mock every step, and the test would
only prove we called methods in a certain order, not that the URL or headers are right.
`MockRestServiceServer` tests what actually goes over the wire.

### Likely interview questions
1. **Why put an interface (`IssueSource`) in front of GitHub?**
   So the code that uses it (backfill, upsert) doesn't depend on GitHub. A Jira source can
   implement the same interface, and tests can pass in a fake. The tradeoff is one extra file,
   which is worth it here because the schema is already designed to work with any tracker.
2. **How do you keep the GitHub token out of the code and out of git?**
   It is only in an environment variable. `application.yml` says `${GITHUB_TOKEN:}`, so Spring
   reads it at startup. The repo only contains the variable's *name*. In production it would come
   from a secret store and be injected as an env var.
3. **What does `MockRestServiceServer` do, and why is it better than calling the real API in a unit test?**
   It plugs in a fake HTTP layer that checks the outgoing request (URL, method, headers) and
   returns a canned response. The test is fast, works offline, never hits the rate limit, and can
   simulate cases that are hard to get from the real API, like a 404 or a page without a Link header.

## M1 refactor + pieces 3 and 4: neutral IssueSource, Link-header paging, PR skip, mapper (3 Nov 2026)

Files:
- moved to `source/`: `IssueSource.java`, `IssuePage.java` (new shape)
- `github/GitHubIssueSource.java` (paging + PR skip), new `github/GitHubIssueMapper.java`
- tests: `GitHubIssueSourceTest.java` (8 tests), new `GitHubIssueMapperTest.java` (4 tests),
  fixtures in `src/test/resources/github/`

### What it does
- **The interface now speaks only "our" language.**
  `IssuePage fetchPage(String repo, String cursor)` returns `IssuePage(List<Issue> issues, String nextCursor)`.
  Callers pass `null` for the first page, then keep passing back `nextCursor` until it is `null`.
- **Paging (piece 3).** GitHub puts the next page's URL in the `Link` response header:
  `<https://api.github.com/repositories/6296790/issues?...&after=Y3Vy...%3D&page=2>; rel="next"`.
  `nextUrl()` finds the part marked `rel="next"` and strips the `< >`. That URL *is* the cursor.
- **Pull requests skipped (piece 4).** GitHub's issues endpoint also returns PRs; only PRs have a
  `pull_request` field, so we drop those.
- **Mapping (piece 4).** `GitHubIssueMapper.toIssue(json)` copies each field into an `Issue`.
  Nested fields: `type.name` -> issueType, `milestone.title` -> milestone, `labels[].name` -> labels.
  The whole JSON goes into `raw` unchanged. `duplicate_of` stays null (a later step fills it).

### Why the interface hides GitHub details
Before the refactor, `IssuePage` returned GitHub JSON and GitHub's `Link` header, and took
`owner, repo` separately. So any caller (the upsert service, the backfill endpoint) would have
to know GitHub's JSON field names and how GitHub paging works. Now:
- **Callers depend only on `Issue` and an opaque cursor.** The upsert service in piece 5 never
  imports anything from `github/`. If GitHub changes its paging (it already moved from `page=N`
  to an encoded `after=` cursor), only `GitHubIssueSource` changes.
- **A Jira source fits without changing callers.** Jira pages with `startAt` numbers, not Link
  headers. A `JiraIssueSource` can use `"100"` as its cursor; the caller's loop stays the same.
- **Tests get easier.** Piece 5 can test the upsert with a tiny fake `IssueSource` that returns
  hand-made `Issue` objects, without any HTTP or JSON.
- The package name says the same thing: `source` is neutral, `github` is one implementation.
This is the **Dependency Inversion** idea: high-level code (backfill) depends on an
abstraction (`IssueSource`), and low-level details (GitHub HTTP) also depend on it.

### Why this way (other choices)
- **Mapper in its own class**: `GitHubIssueSource` does HTTP and paging; `GitHubIssueMapper` does
  JSON -> Issue. Each can be tested alone: the mapper test needs no fake server at all.
- **Repo name taken from GitHub's `repository_url`, not from what the user typed**: GitHub accepts
  `Spring-Projects/Spring-Boot` in URLs, but then the same repo would be stored under two
  spellings. GitHub's own value is always the same.
- **`String.valueOf(json.get("id").asLong())`**: real ids are already bigger than an `int`
  (#52529 has id 6154714728), so `asInt()` would give a wrong number.
- **`URI.create(cursor)`, not `.uri(cursor)`**: the cursor is already URL-encoded (`%3D` means `=`).
  A plain string is treated as a template and encoded *again* (`%3D` -> `%253D`), and GitHub would
  get a broken cursor. Checked: switching to `.uri(cursor)` makes the paging test fail with
  exactly that `%253D`.
- **Only follow cursors that start with `https://api.github.com/`**: every request carries our
  token. If a bad cursor pointed at another server, we'd send it the token. Note the trailing
  `/`: without it, `https://api.github.com.evil.example.com` would pass the check.
- **Loop until `nextCursor` is null, not until a page is empty**: after skipping PRs, a page can
  have zero issues and still have more pages behind it.

### One alternative I rejected
**Paging by page number** (`?page=1`, `?page=2`, ... until an empty page). It looks simpler, but
GitHub's real next links use an `after=` cursor, the Link header is the documented way to page,
and a "stop on empty page" loop would stop too early on a page that held only PRs.

### Basics: the annotations and libraries used here
- **`@Component`** (Spring): marks a class so Spring creates one instance of it at startup (a "bean")
  and can hand it to other classes.
  *Before:* `GitHubIssueMapper mapper = new GitHubIssueMapper();` written by hand everywhere.
  *After:* put `@Component` on the class, and Spring creates it once and passes it in.
- **Constructor injection + `@Autowired`**: Spring calls the constructor and fills each parameter
  with a matching bean. That's how `GitHubIssueSource` gets the mapper.
  *Example:* `public GitHubIssueSource(..., GitHubIssueMapper mapper)` -> Spring passes the mapper.
  `@Autowired` is only needed here because the class has two constructors, so Spring must be told
  which one to use. With a single constructor, Spring uses it automatically.
- **`@Value("${github.token}")`** (Spring): fills a parameter from configuration.
  *Before:* `String token = System.getenv("GITHUB_TOKEN");` *After:* `@Value("${github.token}") String token`,
  and `application.yml` says `token: ${GITHUB_TOKEN:}` (env var, or empty).
- **`@Slf4j`** (Lombok): generates a logger field for you.
  *Before:* `private static final Logger log = LoggerFactory.getLogger(GitHubIssueSource.class);`
  *After:* `@Slf4j` on the class, then just `log.warn(...)`.
- **`record`** (Java 16+): a short way to write a class that only holds data.
  *Before:* a class with 2 private final fields, a constructor, 2 getters, `equals`, `hashCode`, `toString`.
  *After:* `public record IssuePage(List<Issue> issues, String nextCursor) {}`; read with `page.issues()`.
- **`JsonNode`** (Jackson 3, package `tools.jackson.databind`): a tree view of any JSON.
  `json.get("milestone")` gives a child node, `.asString()` / `.asInt()` / `.asLong()` read values,
  `.has("pull_request")` checks for a field, `.isNull()` is true for JSON `null`.
  *Example:* `{"type": {"name": "Bug"}}` -> `json.get("type").get("name").asString()` is `"Bug"`.
  `json.toString()` writes the node back out as JSON text (used for `raw`).
- **`ParameterizedTypeReference<List<JsonNode>>`** (Spring): Java forgets generic types at runtime,
  so `List<JsonNode>.class` can't be written. This small anonymous subclass (`{}` at the end)
  keeps the full type so Spring knows to build a list of `JsonNode`.
- **`MockRestServiceServer`** (spring-test): sits inside RestClient instead of the real HTTP
  connection. `expect(requestTo(url))` says what request must arrive, `andRespond(withSuccess(...))`
  says what to answer. Expectations are checked in order, so the 2-page test also proves page 2
  was asked for *after* page 1, using exactly the cursor URL.

### Likely interview questions
1. **Why does `IssueSource` return a cursor string instead of a page number or GitHub's Link header?**
   Each tracker pages differently (GitHub: Link header URLs with an encoded `after` cursor; Jira:
   `startAt` numbers). An opaque cursor lets every source keep its own method, while callers
   always run the same loop: pass the cursor back until it is null.
2. **What could go wrong if you followed any cursor URL you were given?**
   Every request sends `Authorization: Bearer <token>`. A cursor pointing at another host would
   leak the token there (and it's a form of SSRF). So we only follow URLs that start with
   `https://api.github.com/`, including the slash, so `api.github.com.evil.com` is rejected.
3. **How do you know a GitHub item is a pull request, and why filter it in the source rather than later?**
   GitHub's issues endpoint returns PRs too, and only PRs carry a `pull_request` field. Filtering
   in the GitHub source keeps that GitHub quirk inside the GitHub code: callers only ever see real
   issues, and a Jira source never needs a PR concept.

## M1 finish, step A: IssuePage gets `skipped`, source types fully neutral (4 Nov 2026)

Files: `source/IssuePage.java`, `source/IssueSource.java`, `github/GitHubIssueSource.java`,
`GitHubIssueSourceTest.java` (9 tests now).

Most of step A (the move to `source/`, `fetchPage(repo, cursor)`, `List<Issue>` + `nextCursor`)
was already done in the previous commit. This step adds the last two things.

### What it does
- `IssuePage` now has a third field: `int skipped`, the number of items the tracker sent on
  this page that were *not* issues and were left out. For GitHub those are pull requests.
- `GitHubIssueSource` counts them: each item with a `pull_request` field adds 1 to `skipped`
  instead of being mapped.
- The two `source/` types no longer mention anything GitHub-specific, not even in comments.
  (`IssueSource` used to say "e.g. GitHub sent only pull requests"; now it says
  "every item on it was skipped".) The word "pull request" now only appears in `github/`.

### Why this way
- **Why count skipped at all?** The backfill summary (step D) reports pages, inserted, updated
  and skipped. Without the count, "we stored 30,000 issues" can't be checked against GitHub's
  total, because GitHub's list mixes issues and PRs.
- **Why the neutral name `skipped`, not `pullRequestsSkipped`?** A Jira source might skip other
  things (e.g. sub-tasks). The caller only needs "how many were left out"; *why* is the source's business.
- **Why count it now, in step A, not in step C?** The code already skipped PRs, so passing `0`
  would have been a wrong number. Counting is one `skipped++`.

### Basics: adding a field to a `record`
A record's constructor always takes *all* its fields in order. So
`record IssuePage(List<Issue> issues, String nextCursor)` -> `new IssuePage(issues, cursor)`
becomes
`record IssuePage(List<Issue> issues, String nextCursor, int skipped)` -> `new IssuePage(issues, cursor, skipped)`.
Every old `new IssuePage(a, b)` stops compiling. That's a good thing: the compiler shows you every
place that must now decide what `skipped` is, so none can be forgotten. A new accessor
`page.skipped()` comes for free.

### One alternative I rejected
**Let the caller work it out as `100 - page.issues().size()`.** This breaks on the last page
(which usually has fewer than 100 items), it bakes GitHub's page size into neutral code, and it
mixes up "skipped" with "there were fewer items". The source is the only place that knows
what it left out, so it reports it.

### Likely interview questions
1. **How do you keep an abstraction from leaking details of one implementation?**
   Look at its types and words: here `IssuePage` uses only our `Issue`, a `String` cursor
   nobody opens, and a count. No `JsonNode`, no Link header, no "pull request". If a Jira
   implementation would find a word meaningless, it doesn't belong in the interface.
2. **A page comes back with zero issues. Is the backfill finished?**
   Not necessarily: it could be a page of only PRs (`skipped = 100`) with more pages after it.
   The only "finished" signal is `nextCursor == null`. A test checks exactly this case.
3. **What happens when you add a field to a Java record that is already used?**
   The canonical constructor gets a new parameter, so every existing `new` call fails to compile
   until it passes a value. It's a breaking change, and the compiler helps by finding every call site.

## Setup change: Postgres on host port 5433, database renamed to `triage` (4 Nov 2026)

### What it does
`docker-compose.yml` now maps `"5433:5432"`: port 5433 on the Mac goes to port 5432 inside the
container. `application.yml` connects to `jdbc:postgresql://localhost:5433/triage`.

### Why
A Homebrew Postgres on the Mac already listens on `localhost:5432`, so the app was connecting
to *that* one (which has no `copilot` user) instead of the Docker one. The left number in a port
mapping is the host side, so changing only it avoids the clash; inside the container Postgres
still uses its normal port. The DB name `copilot` was left over from the old project name.

### Gotcha: `POSTGRES_DB` only works on an empty volume
The postgres image creates `POSTGRES_DB` only the *first* time it starts with an empty data
volume. Our volume already existed, so changing `copilot` -> `triage` in the file did nothing on
its own; I ran `CREATE DATABASE triage OWNER copilot` once. A fresh clone gets `triage`
automatically. (The old, empty `copilot` database is still in the volume and can be dropped.)

### One alternative I rejected
**Stopping the Homebrew Postgres** (`brew services stop postgresql`). It works, but it changes
sai's machine outside this project and breaks again the next time that service starts.

### Likely interview questions
1. **In `"5433:5432"`, which side is which?** Left = host (your machine), right = container.
   The app connects to the host side, `localhost:5433`.
2. **You changed `POSTGRES_DB` but the database didn't appear. Why?** The init step only runs
   when the data directory is empty; an existing volume keeps its old databases. Create it by
   hand or (if the data doesn't matter) recreate the volume with `docker-compose down -v`.
3. **How did you find the port clash?** The error was `role "copilot" does not exist`, which is
   odd for a DB we created with that user. `lsof -iTCP:5432 -sTCP:LISTEN` showed two
   listeners: a local `postgres` on 127.0.0.1 and Colima's forwarder on `*`. `localhost` hit the local one first.

## M1 finish, step B: oldest-first paging and rate limits (4 Nov 2026)

Files: `github/GitHubIssueSource.java`, `GitHubIssueSourceTest.java` (14 tests).
Link-header paging was already done (pieces 3+4); this step fills the gaps.

### What it does
- **Oldest first**: the first page URL now ends in `&sort=created&direction=asc`. GitHub keeps
  those settings inside the next-page cursor, so every page stays in date order. Checked on real
  data: spring-petclinic's first item is #1 from 2013.
- **Logs the rate limit every 10 pages**: GitHub sends `X-RateLimit-Remaining` (calls left this
  hour) and `X-RateLimit-Reset` (when the count refills, as Unix seconds) on every answer. Every
  10th page we log e.g. `Fetched 50 pages; rate limit remaining: 4950 (resets at 2026-11-04T11:00:00Z)`.
- **Waits and retries on a rate limit**: if GitHub answers 403 or 429 *because of the rate limit*,
  we wait and ask for the same page again, at most 3 times. How long we wait, in GitHub's order:
  1. `Retry-After: 5` -> 5 seconds.
  2. `X-RateLimit-Remaining: 0` -> until `X-RateLimit-Reset`, plus 1 second in case our clock differs.
  3. Neither (some "secondary" limits) -> 1 minute, as GitHub's docs advise.
  After 3 retries we stop with `"GitHub rate limit still exceeded after 3 retries for ..."`.
- **A 403 that is not a rate limit fails at once** (e.g. "Resource not accessible by personal
  access token"): retrying would never help, so we throw with a clear message that tells you to
  check the token. No error message contains the token (a test checks that).

### How we tell "slow down" from "not allowed"
GitHub uses 403 for both. It counts as a rate limit only if: the status is 429, or it's a 403 *and*
(`X-RateLimit-Remaining` is `0`, or a `Retry-After` header is present, or the message says
"rate limit"). Anything else is a real refusal.

### Basics used here
- **`Supplier<T>`** (Java): an object that holds "some code that gives back a T", run with `get()`.
  We need it because a retry must run *the same HTTP call again*.
  *Before:* the call is written once and runs once: `restClient.get()...toEntity(...)`.
  *After:* `getWithRateLimitRetry("first page", () -> restClient.get()...toEntity(...))`; the helper calls
  `request.get()` as many times as it needs.
- **`java.time.Clock`**: "what time is it?" as an object. Code that calls `Instant.now()` can't be tested
  at a fixed time; code that calls `clock.instant()` can. The app uses `Clock.systemUTC()`, the test uses
  `Clock.fixed(2026-11-04T10:00:00Z)`, so "reset in 30 s" really means 30 s.
- **The `Sleeper` interface**: same idea for waiting. The app passes `duration -> Thread.sleep(duration)`;
  the test passes `waits::add`, which just records the wait. So a test of "wait 31 seconds"
  finishes in milliseconds and can check the exact number.
- **`AtomicInteger`**: a counter that stays correct when two threads add to it at once (`count++` on a
  plain `int` can lose updates). The source is one shared Spring bean, and two backfills could run together.
- **`Thread.currentThread().interrupt()` after `InterruptedException`**: when someone asks a sleeping thread
  to stop, Java throws `InterruptedException` and *clears* the "please stop" flag. Setting it again
  passes the request on to whoever runs the thread, instead of silently swallowing it.
- **`MockRestServiceServer` with `times(4)`**: the same expectation answers 4 requests, which lets the
  test simulate "rate limited on every try".

### One alternative I rejected
**Spring Retry (`@Retryable`)** or **Resilience4j**. Both are good, but they're new dependencies
(not allowed without asking), and the wait time here comes from *GitHub's headers*, which
fixed-backoff annotations don't read easily. A 30-line loop is easy to read and test.
(Another rejected idea: wait proactively when `X-RateLimit-Remaining` gets low. It's nicer to GitHub,
but it wasn't asked for, and the retry already covers running out.)

### Likely interview questions
1. **How do you handle GitHub's rate limit?**
   On 403/429 with rate-limit signs, wait as long as GitHub says (`Retry-After`, else until
   `X-RateLimit-Reset`, else 1 minute), then retry the same page, at most 3 times; then fail clearly.
   Every 10 pages we log how many calls are left. With a token the limit is 5,000 requests/hour.
2. **Why not retry every 403?**
   A 403 can also mean "your token can't read this repo". Retrying that wastes time and hides the
   real problem. We only retry when the headers or message say it's a rate limit.
3. **How do you test code that waits for 30 seconds without the test taking 30 seconds?**
   Inject time and waiting: a fixed `Clock` decides "now", and a fake `Sleeper` records how long
   the code *would* sleep. The test then checks the exact wait (31 s) instantly.

## M1 finish, step D: upsert and backfill loop (piece 5) (4 Nov 2026)

Files: `service/IssueService.java`, `service/BackfillService.java`, `service/BackfillSummary.java`,
`service/UpsertResult.java`, `Issue.updateFrom(...)`; tests `IssueServiceTest` (2), `BackfillServiceTest` (2).

### What it does
- `IssueService.upsert(issue)`: looks the issue up by `(source, externalId)`. Found -> copy the new data
  onto our existing row (`updateFrom`) and save -> `UPDATED`. Not found -> save it -> `INSERTED`.
- `BackfillService.backfill("owner/name")`: starts with cursor `null`, fetches a page, upserts each issue,
  adds up the counts, follows `nextCursor` until it is `null`. Returns
  `BackfillSummary(repo, pages, inserted, updated, skipped, durationMs)`, and logs progress every 10 pages.

### Two deliberate differences from the step D prompt
1. **`backfill` is in `BackfillService`, not `IssueService`.** See "self-invocation" below: inside one class,
   `this.upsert()` would skip the transaction without any error.
2. **`upsert` does not overwrite `duplicate_of` with null.** The prompt says "copy all fields", but GitHub's
   JSON never contains `duplicate_of` (step F fills it). Copying null would erase the answer key every
   time the backfill is re-run. So it's copied only when the incoming value is not null.

### Basics used here
- **`@Service`** (Spring): the same as `@Component` (Spring creates one instance and injects it),
  but the name says "this holds business logic". Purely a label for readers.
- **`@RequiredArgsConstructor`** (Lombok): writes a constructor for every `final` field.
  *Before:* `public IssueService(IssueRepository issueRepository) { this.issueRepository = issueRepository; }`
  *After:* `@RequiredArgsConstructor` on the class; Spring uses that constructor to inject the repository.
- **`@Transactional`** (Spring): "run this method in one database transaction". Spring starts a transaction
  before the method and commits after it (or rolls back if it throws a RuntimeException). It works by
  wrapping the bean in a **proxy**: other beans call the proxy, the proxy opens the transaction, then
  calls the real method.
  **Self-invocation trap:** if a method in the *same* class calls `this.upsert()`, it calls the real object
  directly, the proxy is skipped, and no transaction starts, silently. That's why the loop is in another bean.
- **Managed entity / dirty checking** (JPA): an entity loaded inside a transaction is "managed": Hibernate
  remembers its state, and at commit writes whatever changed (an `UPDATE`) without being asked. So
  `issueRepository.save(row)` in the update path isn't strictly needed; it's there so the reader sees the write.
- **Replacing labels in an `@ElementCollection`:** call `labels.clear(); labels.addAll(newLabels)` on the
  *same* Set. Hibernate replaced our `HashSet` with its own tracking set (`PersistentSet`) when it loaded
  the row; assigning a brand-new `Set` would throw that tracking away.
- **`Optional<Issue>`** (Java): "an Issue, or nothing", instead of returning `null`. `isPresent()` / `get()`.
- **Mockito** (testing): `@Mock IssueRepository` is a fake that does nothing until told;
  `when(repo.find(...)).thenReturn(...)` gives it an answer; `verify(repo).save(x)` checks it was called.
  `@InjectMocks` builds the real `IssueService` with the mocks. In `BackfillServiceTest`, `thenAnswer`
  makes the mock remember saves in a `HashMap`, so the second run can "find" the first run's rows.
- **`System.nanoTime()` for durations:** `currentTimeMillis()` is wall-clock time and can jump (NTP sync,
  clock changes); `nanoTime()` only ever moves forward, so it's the right tool for "how long did it take".

### One alternative I rejected
**One transaction for the whole backfill** (put `@Transactional` on `backfill`). That would keep tens
of thousands of entities in memory until the end, hold one very long transaction, and one bad issue on
page 400 would roll back all 400 pages. One transaction per issue is slower, but simple and safe to resume.
(A middle ground, one transaction per page, is a possible later optimisation.)

### Likely interview questions
1. **How does your backfill stay safe to run twice?**
   Every issue is matched on `(source, external_id)`, the same columns as the database's unique constraint.
   Found -> update, not found -> insert. The test runs the same data twice: the second run inserts 0.
   If two runs raced, the unique constraint would reject the second insert instead of allowing a duplicate.
2. **Why didn't you put `backfill` and `upsert` in the same class?**
   `@Transactional` works through a Spring proxy. A call from inside the same class (`this.upsert()`)
   bypasses the proxy, so no transaction starts and nothing warns you. Splitting into two beans means
   `BackfillService` calls `IssueService` through the proxy.
3. **What is dirty checking?**
   Hibernate keeps a snapshot of every entity it loaded in the current transaction. At commit it compares
   each entity with its snapshot and writes an `UPDATE` for whatever changed. So changing a field on a
   managed entity is enough to save it.

## M1 finish, step E: `POST /backfill/{owner}/{repo}` (piece 6) (4 Nov 2026)

Files: `web/BackfillController.java`, test `web/BackfillControllerTest.java` (3 tests).

### What it does
`curl -X POST localhost:8080/backfill/spring-projects/spring-petclinic` runs the backfill and, when it's
done, answers with the summary as JSON:
`{"repo":"spring-projects/spring-petclinic","pages":12,"inserted":...,"updated":0,"skipped":...,"durationMs":...}`.
Errors come back as standard "problem details" JSON: unknown repo -> 404, bad repo name -> 400.

### Synchronous vs background: the trade-off
*Synchronous* (what we do): the HTTP request stays open until the backfill finishes.
- Good: dead simple; the caller gets the real result or the real error; easy to test; nothing to poll.
- Bad: spring-boot takes minutes, so the request is long. If the client (curl, a proxy, a load balancer)
  gives up, the caller loses the summary (the backfill itself keeps running on the server). It also ties
  up one web thread for the whole time, and nothing stops two people starting the same backfill at once.
*Background* (later): `POST` answers `202 Accepted` with a job id at once; the work runs on another
thread (`@Async`, or better a Kafka message, which this project already plans to use); `GET /jobs/{id}`
shows progress. More robust, but needs job state, a status endpoint and more tests. Fine to wait until
the backfill is triggered by something other than a developer with curl.

### Basics used here
- **`@RestController`** (Spring MVC): marks a class whose methods answer HTTP requests, and whose return
  values are written as JSON (it's `@Controller` + `@ResponseBody`).
  *Before (plain servlet):* read the URL, parse it, call the service, turn the result into JSON, write it to the response.
  *After:* `@PostMapping("/backfill/{owner}/{repo}") public BackfillSummary backfill(...)`; Spring does the rest.
- **`@PostMapping("/backfill/{owner}/{repo}")`**: this method handles `POST` to that path; `{owner}` and
  `{repo}` are placeholders. **`@PathVariable String owner`** puts the placeholder's value into the parameter.
  POST (not GET) because it *changes* data; a browser or crawler following a GET link must never start a
  backfill. A test checks that GET gives 405 Method Not Allowed.
- **Records as JSON:** Jackson writes a record's components as fields: `BackfillSummary(repo, pages, ...)`
  -> `{"repo": ..., "pages": ...}`. No annotations needed.
- **`@ExceptionHandler`**: "if this controller throws X, answer like this instead of a 500".
  **`ProblemDetail`** is Spring's built-in RFC 9457 error body: `{"status":404,"title":"Not Found","detail":"..."}`.
- **`MockMvc` standalone setup** (spring-test): sends fake HTTP requests to the controller in memory, through
  real Spring MVC (URL matching, JSON, exception handlers), without starting a server, the app or a DB.
  We use this instead of `@WebMvcTest` because in Spring Boot 4 that lives in an extra module
  (`spring-boot-webmvc-test`) we would have to add.
- **`jsonPath("$.inserted")`**: picks a value out of the JSON response; `$` is the root object.

### One alternative I rejected
**`@Async` with a fire-and-forget `202 Accepted`.** It looks like a one-line improvement, but then the caller
can't see the result or errors, there's no progress or job id, and failures only show up in the logs.
Doing background work properly needs job tracking, which is a bigger piece than this step.

### Likely interview questions
1. **Why is the backfill a POST and not a GET?**
   GET must be safe (no side effects): browsers prefetch links, crawlers follow them, proxies may repeat
   them. A backfill writes thousands of rows and uses rate limit, so it's a POST.
2. **What are the downsides of running the backfill inside the HTTP request?**
   Long request (clients/proxies may time out and lose the summary), a web thread is busy for minutes, no
   progress, and no protection against two runs at once. The fix is a background job (Kafka or `@Async`)
   that returns a job id immediately, plus a status endpoint.
3. **How do you test a controller without starting the whole app?**
   `MockMvcBuilders.standaloneSetup(new BackfillController(mockService))`: real MVC routing, JSON and
   exception handling, a Mockito mock for the service, no server and no database.

## M1 finish, step F: the answer key, `duplicate_of` (4 Nov 2026)

Files: `source/DuplicateSource.java`, `source/DuplicateLink.java`, `github/GitHubDuplicateSource.java`,
`service/DuplicateService.java`, `service/DuplicateSummary.java`, two new `IssueRepository` methods,
`POST /backfill/{owner}/{repo}/duplicates` in `BackfillController`; tests `GitHubDuplicateSourceTest` (18),
`DuplicateServiceTest` (2), one more controller test.

### What I found in the real data first (curl, 4 Nov 2026)
- **#52529** (closed as duplicate): the REST timeline has only `closed` (with `state_reason: duplicate`) and
  label events. **No comment, no `marked_as_duplicate` event, and nothing in REST says which issue it
  duplicates.** GitHub's **GraphQL** API does: `ClosedEvent.duplicateOf` = **#52519**. That's set when a
  maintainer uses "Close as duplicate of #N".
- **Only 178 spring-boot issues have `state_reason=duplicate`, but 2,011 have the `status: duplicate` label.**
  Old issues were back-filled by GitHub as `state_reason: completed` (not null, as `docs/problem.md`
  assumed), and 2023-2024 ones are often `not_planned`. So the label is the main signal, and the step
  checks both.
- A sample of 20 labelled duplicates from 2013 to 2026 showed four kinds:
  1. Recent ones: `ClosedEvent.duplicateOf` (e.g. #47366 -> #46944, #48342 -> #48300). Reliable.
  2. A maintainer comment: "Duplicate of #16381", "Duplicates https://github.com/spring-projects/spring-boot/issues/49910".
     (Search finds ~717 labelled duplicates with "Duplicate of" in a comment.)
  3. A comment pointing to **another repo**: "This is a duplicate of https://github.com/spring-projects/spring-framework/issues/31892".
     Can't be stored: `duplicate_of` is a number in the same repo.
  4. Vague or no link: "Yes, see #52367", "we fixed it in #1800", or no comment at all (common before ~2016).
- **Surprise:** on #16344 the maintainer wrote "Duplicate of #16381", but the GraphQL `MarkedAsDuplicateEvent`
  lists #16344 as the *canonical* one, the opposite way. So the event's direction isn't trusted;
  it's only read as "these two are linked".

### The rules ("only fill it when sure")
1. If the **latest** close was "close as duplicate of #N" -> **FOUND** (evidence `CLOSE_REASON`).
   Latest, because an issue can be closed, reopened and closed again (#52124).
2. Otherwise collect candidates from "marked as duplicate" links (the *other* issue of the pair; ignored if
   someone later un-marked it) and from **maintainer** comments (`OWNER`/`MEMBER`/`COLLABORATOR`) matching
   `duplicate(s|d) (of) #N | gh-N | https://github.com/<owner>/<repo>/issues/N`.
   Exactly one candidate -> **FOUND**; more than one -> **AMBIGUOUS**; none -> **NOT_FOUND**.
3. A FOUND original in another repo becomes **OTHER_REPO** (not stored). Self-references are ignored.
   "duplicated by #N" (other direction) and "see #N" (vague) deliberately don't match.
The summary counts every outcome: `checked = found + notFound + otherRepo + ambiguous`, and `found` is split by evidence.

### Basics used here
- **GraphQL**: one endpoint (`POST /graphql`); the request says exactly which fields it wants, as nested
  text. `query($number: Int!) { repository(...) { issue(number: $number) { ... } } }`. The `$number` values
  go in a separate `"variables"` object, so the query text never changes (no string-building, no injection).
  `... on ClosedEvent { duplicateOf { ... } }` means "if this item is a ClosedEvent, also give me these fields".
  GraphQL usually answers **HTTP 200 even on errors**, with an `"errors"` list; the code checks it.
- **`Pattern` / `Matcher`** (Java regex): `Pattern.compile(...)` once (it's slow to build), then
  `matcher(text)` and `while (m.find())` walks through every match; `m.group(1)` is the first `( )` part.
  `(?i)` makes it case-insensitive, `\\b` means "word boundary" (so "nonduplicate" doesn't match).
- **`@Query` + `@Modifying`** (Spring Data JPA): write the JPQL yourself when a method name can't express it.
  JPQL talks about *entities and fields* (`Issue i`, `i.stateReason`), not tables and columns.
  `left join i.labels l` joins the `@ElementCollection`, and `l` is then one label string.
  `@Modifying` marks an `update`/`delete` query (not a select); it needs a transaction, so the method has `@Transactional`.
  *Before:* load the issue (and maybe its labels), set the field, save. *After:* one `UPDATE issue SET duplicate_of = ? WHERE id = ?`.
- **`@Param("repo")`**: ties a method parameter to `:repo` in the query.
- **Lambda as a fake interface:** `DuplicateSource` has one method, so the test writes
  `DuplicateSource source = (repo, number) -> answers.get(number);`, a complete fake with no mocking library.
- **Records with a "compact constructor"**: `record Target(String repo, int number) { Target { repo = repo.toLowerCase(...); } }`
  runs before the fields are set, so every `Target` is stored lower-case and `equals` ignores case.

### One alternative I rejected
**Using any `#N` in a maintainer's comment** ("see #123", "like #123"). It would fill many more rows, but a
wrong answer key is worse than a missing one: the replay test (M3) would mark our model wrong when it is
right. So vague references count as NOT_FOUND, and the report says how many there are.
(Also rejected: REST timeline only. It's simpler, but it cannot see "close as duplicate of", the best signal.)

### Likely interview questions
1. **How did you build the ground truth for duplicates, and how do you know it's right?**
   From GitHub's own records, strongest first: "close as duplicate of #N" (GraphQL `ClosedEvent.duplicateOf`),
   then "marked as duplicate" links and maintainer comments like "Duplicate of #N", which must agree on one issue.
   Vague mentions are ignored, other-repo originals are counted but not stored, and the summary reports
   found / not found / ambiguous / other repo, so the coverage is visible, not hidden.
2. **Why did you need GraphQL when everything else uses REST?**
   The REST timeline for #52529 shows "closed, reason duplicate" but not *which* issue. Only GraphQL exposes
   `duplicateOf` on the close event. It needs a token, and errors come back as HTTP 200 with an `errors` list.
3. **What biases does this answer key have?**
   It favours recent issues (structured close reason) and duplicates a maintainer bothered to link; old ones
   with no link are missing. Also, maintainers mostly spot duplicates that *look* alike (docs/problem.md),
   so the key leans towards easier cases. We report the not-found share honestly.

## M1 finish, step G: `GET /repos/{owner}/{repo}/issues` (piece 7) (4 Nov 2026)

Files: `web/IssueController.java`, `service/IssueSummary.java`, `service/IssueList.java`,
`IssueService.listIssues`, two new `IssueRepository` methods, `application.yml` (`open-in-view: false`);
tests `IssueServiceListTest` (3), `IssueControllerTest` (4).

### What it does
`curl 'localhost:8080/repos/spring-projects/spring-petclinic/issues?page=0&size=20'` returns
`{"issues":[{"number":..,"title":..,"state":..,"stateReason":..,"labels":[..],"createdAt":..,"duplicateOf":..}],"page":0,"size":20,"total":N}`,
newest first. `size` must be 1-100, `page` 0 or more (else 400).

### The N+1 problem, and how this avoids it
Labels live in another table and are **lazy**: Hibernate loads them only when you first touch `issue.getLabels()`.
Load 20 issues (1 query), then read each one's labels (20 more queries) = **N+1 = 21 queries** for one page.
With 100 issues it's 101. It's invisible in the code and only shows as slowness or a wall of SQL in the log.
The fix: load issues *and* labels in one query, with a join. Two ways:
- **Fetch join** in JPQL: `select i from Issue i left join fetch i.labels where ...`
- **`@EntityGraph(attributePaths = "labels")`** on a repository method: "when you run this query, also fetch
  labels". Same SQL, no hand-written JPQL. Used here.

**But a collection fetch + paging don't mix.** With a join, one issue with 3 labels becomes 3 rows, so the
database can't do `LIMIT 20` on *issues*. Hibernate then loads **all** matching rows and pages in memory
(warning `HHH90003004`): for spring-boot that's every issue, for every page. So it takes two queries:
1. `findIdsByRepo(repo, pageable)`: just the 20 ids for this page, `ORDER BY number DESC LIMIT 20 OFFSET ..`,
   plus a `count(*)` for the total. (Spring Data runs the `countQuery` automatically for a `Page`.)
2. `findByIdInOrderByNumberDesc(ids)` with `@EntityGraph("labels")`: those 20 issues and their labels, in one join.
Total: **3 SQL statements per page (ids, count, issues+labels), whatever the page size.**

### Why a DTO, never the entity
- The entity's `labels` is lazy. Turning it into JSON *after* the transaction ends throws
  `LazyInitializationException`, or (with open-in-view on) silently fires N+1 queries while writing the response.
- The entity has `raw` (the whole GitHub JSON, KBs per issue) and `body`: we'd send far too much.
- The API would change whenever the table changes. A record (`IssueSummary`) is a fixed contract.

### Basics used here
- **`Pageable` / `PageRequest.of(page, size, sort)`** (Spring Data): "page 2, 20 per page, newest first". Pass it
  to a repository method and Spring adds `ORDER BY ... LIMIT ... OFFSET ...`.
  **`Page<T>`** is the answer: `getContent()` (this page) + `getTotalElements()` (all pages, from the count query).
- **`@EntityGraph(attributePaths = "labels")`**: tells this one query to fetch the lazy `labels` too (a join).
  *Before:* `findByIdIn(ids)` then 20 lazy loads. *After:* one query with `left join issue_label`.
- **Derived query names**: `findByIdInOrderByNumberDesc(ids)`: Spring reads the method name and builds
  `where id in (...) order by number desc`. No SQL written.
- **`@Transactional(readOnly = true)`**: a read-only transaction; Hibernate skips dirty checking at the end.
- **`@GetMapping` + `@RequestParam(defaultValue = "20") int size`**: reads `?size=50` from the URL, or uses 20.
- **`spring.jpa.open-in-view: false`**: Spring Boot's default (`true`) keeps a DB session open until the HTTP response is
  written, so lazy loading "just works" in controllers and JSON writing. That hides N+1 queries and holds DB connections
  longer. Turning it off makes a missed fetch fail loudly in development instead of being slow in production.
- **`ArgumentCaptor`** (Mockito): catches the argument a mock was called with, so the test can check the
  `Pageable` (page 3, size 20, sorted by number desc).

### One alternative I rejected
**`@BatchSize(size = 100)` on `labels`.** One annotation, and Hibernate then loads labels for up to 100
issues in one `IN (...)` query when the first one is touched: 1 + 1 queries instead of N+1. It's a good tool,
but it changes *every* place that reads labels and is less obvious to a reader than an explicit
"load these issues with their labels" method. (Also rejected: a single `@EntityGraph` + `Page` query, because of
the in-memory paging trap above.)

### Likely interview questions
1. **What is the N+1 problem and how did you avoid it?**
   Loading N parents with 1 query and then each lazy child collection with its own query: N+1 round trips.
   I page the ids first, then load those issues with `@EntityGraph(labels)`, one join. 3 statements per page.
2. **Why not just add `join fetch` to the paged query?**
   A collection join multiplies rows, so the database can't `LIMIT` by issue. Hibernate fetches everything and
   pages in memory (HHH90003004), which is fine for 20 rows and terrible for 30,000. Page the ids, then fetch.
3. **Why return DTOs instead of entities?**
   Lazy collections break (or cause hidden queries) during JSON writing, entities carry fields the API shouldn't
   expose (`raw`, `body`), and the API contract shouldn't change every time the table does.

(`PostgresContainerConfig`, `PostgresTest`, `IssueRepositoryDbTest` (4), `IssueServiceDbTest` (2)).
Also: README/CLAUDE.md "Start DB" fixed, docs/problem.md and schema.md corrected (old duplicates show
`completed`, not NULL), the empty `copilot` database dropped.

### What it does
- **Flyway owns the schema now.** On startup Flyway looks at its table `flyway_schema_history`, sees which
  `V<n>__*.sql` files have not run yet, and runs them in order, each exactly once.
- **V1** is the schema as it was (from `pg_dump --schema-only`), minus Hibernate's `CHECK (source = 'GITHUB')`.
  **V2** drops that CHECK with `IF EXISTS` (the old DB has it; a fresh one built from V1 doesn't).
- **The existing DB (44,204 rows) was "baselined":** `baseline-on-migrate: true` + `baseline-version: 1` means
  "this DB already has V1's tables; record it as version 1 without running V1". Then only V2 ran.
  Checked: history shows `1 << Flyway Baseline >>` and `2 drop source check`; the CHECK is gone; data intact.
- **`ddl-auto: validate`**: Hibernate no longer changes tables; at startup it only checks that every entity
  field has a matching column of a compatible type, and refuses to start otherwise.
- **Real-DB tests**: Testcontainers starts a throw-away `postgres:16` in Docker; Flyway builds it from V1 + V2
  (proving the migrations work on an empty DB); the tests run real SQL against it.

### Why not `ddl-auto: update` in production
- It only ever *adds* (new tables, new columns). It never drops or renames, never changes a type, and never
  migrates data. Rename a field and you get a second, empty column next to the old one.
- It's not reviewed or versioned: nobody sees the exact SQL before it runs on the production DB, and you
  can't tell which schema version a database is at.
- It adds things you didn't ask for, like our `CHECK (source = 'GITHUB')`, which would have rejected Jira rows,
  and it would never remove that CHECK by itself.
- Every app instance tries to change the schema when it starts; with several instances that's a race.
With Flyway every change is a SQL file in git: reviewed, versioned, run once, in order, on every environment.

### Basics used here
- **Flyway file names:** `V2__drop_source_check.sql` = version 2, description "drop source check" (two underscores).
  Never edit a file that has already run: Flyway stores a checksum and refuses to start if it changes. Add V3 instead.
  *Before:* change `Issue.java`, restart, hope Hibernate does the right thing. *After:* write `V3__add_x.sql`, review it, restart.
- **Baseline:** "adopt" a database that existed before Flyway. Without it, Flyway would try to run V1's
  `CREATE TABLE issue` on a DB that already has it, and fail.
- **Testcontainers:** a Java library that starts real Docker containers for tests and removes them afterwards.
  *Before:* tests against H2 (an in-memory DB that isn't Postgres: no `jsonb`, different SQL) or a shared dev DB.
  *After:* `new PostgreSQLContainer("postgres:16")`: the same database as production, fresh for each run.
- **`@ServiceConnection`** (Spring Boot): put it on a container bean and Boot points the DataSource (and Flyway)
  at that container. No URLs or passwords in test config.
- **`@DataJpaTest`**: starts only the database part of the app (entities, repositories, Flyway, JdbcTemplate).
  Each test runs in a transaction that is **rolled back** at the end, so tests can't see each other's rows.
  `@AutoConfigureTestDatabase(replace = NONE)` says "use our Postgres, don't swap in an embedded DB".
- **One container for all tests:** Spring caches a test context and reuses it for every test class with the
  same configuration. All real-DB classes extend `PostgresTest`, so the container starts once (~3 s), not per class.
- **Counting SQL statements:** with `hibernate.generate_statistics=true`, `Statistics.getPrepareStatementCount()`
  counts the statements Hibernate sent. The test asserts **exactly 3** for a page of 20 issues with labels.
- **`entityManager.flush()` then `clear()`:** flush sends pending SQL now; clear forgets every loaded entity,
  so the next read really goes to the database (like a new request).
- **Maven profile with file activation:** the `colima` profile turns itself on only if
  `~/.colima/default/docker.sock` exists, and tells Testcontainers where Docker is. On a normal Docker machine
  or in CI it stays off. (Running tests from VS Code doesn't use Maven, so there `DOCKER_HOST` must be set.)

### One alternative I rejected
**Recreating the database from V1 instead of baselining** (`docker-compose down -v`, then let Flyway run V1, V2
and re-run the backfill). Clean, but it throws away 44k rows and the answer key and costs ~30 minutes of API
calls. Baselining keeps the data and still gives a schema that V1 + V2 can rebuild from scratch (the tests prove that).
Also rejected: H2 for tests. It's fast but isn't Postgres (no `jsonb`, different SQL), so it would test the wrong database.

### Likely interview questions
1. **How do you introduce Flyway into a project whose database already exists?**
   Write V1 = the current schema (from `pg_dump --schema-only`), set `baseline-on-migrate` with baseline version 1,
   so the existing DB is marked as V1 without running it. Further changes are V2, V3... Fresh databases (tests,
   new environments) run V1 for real. Make sure V1 + V2 give the same schema on both.
2. **Why `ddl-auto: validate` and not `update`?**
   `update` only adds, is not reviewed or versioned, races between instances, and even added a CHECK we didn't
   want. `validate` lets Flyway own the schema and still fails fast if an entity doesn't match the table.
3. **Why Testcontainers instead of H2 or mocks for repository tests?**
   Mocks don't run SQL at all; H2 runs a different SQL dialect. Testcontainers runs the real Postgres 16, so the
   unique constraint, `jsonb`, the JPQL queries and the migrations are all tested for real.

## M2 step 1: Kafka in docker-compose, topics `issue-events` and `issue-events.DLT` (4 Nov 2026)

Files: `docker-compose.yml` (service `kafka`), `kafka/KafkaTopicsConfig.java`, test `KafkaTopicsConfigTest` (2).

### What it does
- `docker-compose up -d` now also starts **one Kafka broker** (`apache/kafka:4.1.0`) on `localhost:9092`, in
  **KRaft mode**: the broker keeps its own metadata (which topics exist, who leads which partition), so no
  separate ZooKeeper service is needed.
- When the app starts, Spring's `KafkaAdmin` creates the two `NewTopic` beans if they don't exist:
  `issue-events` (3 partitions) and `issue-events.DLT` (3 partitions, for messages that keep failing).
  Checked with `kafka-topics.sh --describe`: both topics exist, 3 partitions, leader = broker 1.
- Auto-creating topics is switched off in the broker, so a typo in a topic name fails loudly.

### Partitions, keys and consumer groups: a small example
A **topic** is a named log of messages. It is split into **partitions**; each partition is an ordered list,
and Kafka only guarantees order *within* one partition.
The **key** decides the partition: `partition = hash(key) % 3`. We'll use the key `owner/repo#number`:
```
issue-events   partition 0: [octo/hello#7 opened] [octo/hello#7 labeled] [octo/hello#7 closed]   <- one issue, in order
               partition 1: [octo/hello#2 opened] [octo/web#5 edited]
               partition 2: [octo/hello#9 opened]
```
All events of issue #7 have the same key, so they land in the same partition and are read in the order they
were written: "closed" can't be processed before "opened".
A **consumer group** is a team of consumers sharing the work. Kafka gives each partition to exactly one member:
```
group "triage-worker", 1 instance  -> it reads partitions 0, 1, 2
group "triage-worker", 3 instances -> each reads one partition (3x the throughput)
group "triage-worker", 4 instances -> one sits idle: never more busy consumers than partitions
another group, e.g. "analytics"   -> gets its OWN copy of every message, independent of triage-worker
```
So partitions are the unit of parallelism (3 here), keys keep related messages in order, and groups let
different jobs each read everything.

### Basics used here
- **`NewTopic` + `TopicBuilder`** (Spring Kafka): describe a topic in code; `KafkaAdmin` creates it at startup.
  *Before:* run `kafka-topics.sh --create --topic issue-events --partitions 3 ...` by hand on every machine.
  *After:* `TopicBuilder.name("issue-events").partitions(3).replicas(1).build()` as a `@Bean`.
- **`@Configuration` + `@Bean`**: a class whose `@Bean` methods return objects for Spring to manage.
- **Replication factor**: how many brokers keep a copy of each partition. 1 here (one broker); production uses 3
  so a broker can die without losing messages.
- **Dead-letter topic (DLT)**: where a message goes after its retries are used up, so one bad message doesn't
  stop everything behind it in the partition. Same partition count as the main topic, because by default a
  failed message is sent to the *same partition number* in the DLT.
- **KRaft listeners**: `PLAINTEXT://:9092` is for clients, `CONTROLLER://:9093` for the broker's internal voting;
  `ADVERTISED_LISTENERS=localhost:9092` is the address the broker tells clients to use (the app runs on the Mac).

### One alternative I rejected
**The Bitnami or Confluent images, or ZooKeeper-based Kafka.** The prompt asks for the official Apache image,
it's what the Kafka project itself publishes, and ZooKeeper was removed in Kafka 4.0, so KRaft is the only
option going forward. Also rejected: a Docker volume for Kafka data. The image runs as a non-root user, so a fresh
volume needs ownership fixes, and in development Postgres, not Kafka, is the source of truth.

### Likely interview questions
1. **How do you keep events for one issue in order with 3 partitions?**
   Use the issue as the message key (`owner/repo#number`). The same key always hashes to the same partition, and
   Kafka keeps order within a partition. Different issues can still be processed in parallel.
2. **What happens if you run 5 consumers in a group on a 3-partition topic?**
   3 get one partition each; 2 are idle (standby). Partitions limit parallelism, so pick the count for the
   throughput you expect. Adding partitions later changes which partition a key maps to.
3. **What is KRaft?**
   Kafka's built-in consensus (Raft) for cluster metadata, replacing ZooKeeper. A node can be broker, controller
   or both; here one node is both. Since Kafka 4.0 it's the only mode.

## M2 step 2: webhook receiver `POST /webhooks/github` (4 Nov 2026)

Files: `github/WebhookSignatureVerifier.java`, `github/GitHubWebhookController.java`, `application.yml`
(`github.webhook-secret: ${GITHUB_WEBHOOK_SECRET:}`); tests `WebhookSignatureVerifierTest` (5),
`GitHubWebhookControllerTest` (9).

### What it does
GitHub sends an HTTP POST to us whenever something happens to an issue (a **webhook**). The receiver, in this order:
1. No secret configured -> **503** and an error log line `GITHUB_WEBHOOK_SECRET is not set: refusing ...`.
2. `X-Hub-Signature-256` missing or wrong -> **401**. The body is never logged.
3. `X-GitHub-Event: ping` (sent once when the webhook is created) -> **200** `pong`.
4. `issues` with action opened / edited / closed / reopened / labeled / unlabeled -> **200** (step 3 hands it to Kafka).
5. Any other event or action -> **202** "ignored". (A signed body that isn't JSON -> 400.)
It does no GitHub calls and no triage work: GitHub gives up after 10 seconds and marks the delivery as failed.

### How the signature works (HMAC)
GitHub and we share a secret. For each delivery GitHub computes `HMAC-SHA256(secret, body)` and sends it as
`sha256=<64 hex chars>`. We compute the same over the body we received; if both match, the sender knew the
secret (so it's GitHub) and the body wasn't changed on the way. Checked against GitHub's documented example:
secret `It's a Secret to Everybody`, body `Hello, World!` -> `sha256=757107ea...b043e17`.

### Why raw bytes, why constant time
- **Raw bytes:** the signature is over the *exact bytes* sent. If we parsed the JSON into an object and wrote it
  back out, spacing, key order or number formats could change and a genuine request would fail the check.
  So the controller takes `@RequestBody byte[]`, verifies, and only then parses.
- **Constant-time compare (`MessageDigest.isEqual`):** a normal `equals` stops at the first different character.
  An attacker can measure that tiny time difference and find the right signature one character at a time.
  `isEqual` always compares everything, so the time doesn't leak anything.

### Basics used here
- **`@RequestHeader(value = "X-GitHub-Event", required = false) String event`**: puts an HTTP header into a
  parameter (null if missing, instead of Spring answering 400 itself, so *we* decide: 401).
- **`@RequestBody byte[] body`**: the body untouched. *Before:* `@RequestBody IssueEvent event` (Spring parses
  JSON first; the original bytes are gone). *After:* `byte[]`, verify, then `jsonMapper.readTree(body)`.
- **`ResponseEntity`**: lets a controller choose the status code: `ResponseEntity.status(401).body("...")`,
  `ResponseEntity.accepted()` (202), `ResponseEntity.ok(...)` (200).
- **`javax.crypto.Mac`**: the JDK's HMAC. `Mac.getInstance("HmacSHA256")`, `init(new SecretKeySpec(secretBytes, ...))`,
  `doFinal(body)`; `HexFormat.of().formatHex(...)` turns the 32 bytes into 64 lowercase hex characters.
- **`JsonMapper`** (Jackson 3): Spring Boot creates one; we inject it and call `readTree(bytes)` to get a `JsonNode`.
- **Status codes:** 200 = done; 202 = received, nothing to do; 401 = we don't believe you're GitHub; 503 = we're not
  configured, try later (GitHub shows it as a failed delivery, which can be redelivered once the secret is set).

### One alternative I rejected
**A servlet filter or Spring Security for the signature check.** Cleaner if many endpoints needed it, but there's one
webhook endpoint, and a filter would have to cache the body so the controller can read it again (a body stream can
only be read once). Doing it in the controller with `byte[]` is short and visible. Also rejected: answering 401 when
the secret is missing. 401 means "you aren't GitHub", but the real problem is *our* configuration, so 503 plus a log line.

### Likely interview questions
1. **How do you know a webhook really came from GitHub?**
   HMAC-SHA256 of the raw body with a shared secret, compared with `X-Hub-Signature-256` in constant time. Wrong or
   missing -> 401, and the body is never logged. The secret comes only from an environment variable.
2. **Why must you verify the raw body before parsing JSON?**
   The signature covers the exact bytes. Parsing and re-serializing can change whitespace, key order or number
   format, so even a genuine request would fail, or you'd end up checking something other than what was sent.
3. **GitHub waits 10 seconds. How do you stay under that?**
   The receiver only verifies, reads the event type and hands the payload on (Kafka, step 3). No GitHub API calls,
   no triage. The slow work happens in a consumer that GitHub doesn't wait for.
